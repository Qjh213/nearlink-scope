# M5 · 单变量实验矩阵与可解释评分

## 1. 阶段目标

M5使用M1–M4已经验收的固件和PC测量链路，研究距离、2.4 GHz干扰、Payload和目标速率变化时，
当前H3863与SDK组合的应用链路指标如何变化。它不是协议极限测试，也不把单次环境结果外推为通用性能。

主链路固定为SLE Write Command，原因是M1已完成同板稳定基线，且Command不会把协议层写确认混入业务事务。
M2的BLE同语义结果作为背景参考，不再复制整套M5矩阵，避免实验规模无边界扩张。

## 2. 固定条件

| 项目 | 固定值 |
|---|---|
| 板卡 | 同一对BearPi-Pico H3863，COM3 initiator、COM4 responder |
| 写语义 | SLE Write Command |
| Window | 1 |
| Timeout | 50 ms |
| SLE连接参数请求 | intv=24（运行日志还必须确认实际授予值） |
| 串口 | 115200/8N1、无流控、DTR/RTS关闭 |
| 单轮正式时长 | 180 s，从完整平台签名ready后开始 |
| 重复次数 | 每个条件2轮；基线在整套实验开头和结尾各做1轮 |
| 固件身份 | 每个cfg保存SHA-256与strings身份检查 |
| 主指标 | p50/p90/p99/p99.9/max、mean、jitter、timeout/dup/ooo/bad/drop、实际速率 |

距离和干扰实验期间Payload固定40 B、目标速率固定40 Hz。Payload实验期间距离固定为近距基线、速率40 Hz；
速率实验期间距离固定为近距基线、Payload固定40 B。

## 3. 最小正式矩阵

`cfg`写入每个REQ和平台签名，编号不能重复使用。

| cfg | 变量组 | 条件 | Payload | 目标速率 | 现场动作 |
|---:|---|---|---:|---:|---|
| 500 | baseline | 近距、常规环境 | 40 B | 40 Hz | 开始和结尾各一轮 |
| 511 | payload | 最小负载 | 12 B | 40 Hz | 不移动板卡 |
| 512 | payload | 中等负载 | 100 B | 40 Hz | 不移动板卡 |
| 513 | payload | 大负载 | 250 B | 40 Hz | 先做60秒冒烟确认MTU与帧长 |
| 521 | rate | 低速 | 40 B | 10 Hz | 不移动板卡 |
| 522 | rate | 中速 | 40 B | 25 Hz | 不移动板卡 |
| 523 | rate | 边界探索 | 40 B | 60 Hz | 允许实际速率低于目标，但必须记录原因证据 |
| 531 | distance | 中距 | 40 B | 40 Hz | 实测并记录距离、遮挡和板卡朝向 |
| 532 | distance | 远距 | 40 B | 40 Hz | 不预设“极限距离”，以现场可重复位置为准 |
| 541 | interference | 受控2.4 GHz负载 | 40 B | 40 Hz | 固定干扰源、距离、业务和持续时间 |

基线近距建议0.5 m；中距建议3 m；远距建议8 m，但最终必须记录现场实测值，不能只使用“近/中/远”。
如果现场不具备8 m直视空间，选择两个可重复位置代替，不为了凑数字改变环境定义。

## 4. 执行顺序与停止条件

1. 每个新固件先运行60秒冒烟；身份、cfg、Payload、rate、MTU、intv与ready必须完整。
2. 冒烟通过后执行两轮180秒正式采集；两轮之间重新复位并形成新会话。
3. 开头与结尾重复cfg=500，用于检查环境漂移；若基线p50或p99变化超过预先记录的10%，当天矩阵不直接合并。
4. 出现断链、连续timeout、bad或drop增长时停止该轮，保留失败日志，不能只重跑并删除失败证据。
5. 60 Hz是能力边界探索，不预设一定稳定；实际完成速率本身就是结果。

## 5. 干扰条件的最低记录要求

“打开Wi-Fi”不是可复现实验。干扰轮至少记录：

- 干扰源设备与频段；
- 干扰源到两块板的距离；
- 使用的信道或无法确认信道的事实；
- 持续业务类型，例如局域网持续传输；
- 实验开始与结束时间；
- 板卡位置、朝向和供电均未改变。

如果无法固定这些条件，干扰轮只能作为探索性观察，不能进入正式评分。

## 6. 评分原则

评分是结果索引，不替代原始指标。M5先输出完整指标表，再根据明确目标生成四个分项：

- 时延：p50与p99；
- 稳定：jitter与max；
- 可靠：timeout、duplicate、out-of-order和bad；
- 采集完整：板端drop、PC缺口和平台签名完整性。

阈值必须写进报告配置并可修改，不把当前基线自动包装成协议合格线。任何发生断链、bad>0、drop>0或签名
不完整的轮次都标记为“不可评分”，而不是用较低总分掩盖证据问题。
