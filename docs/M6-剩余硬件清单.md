```powershell
$log = 'E:\nearlink-scope\out\longrun_monitor_2h.csv'
"time,ws_mb,handles,threads" | Set-Content $log
while ($true) {
  $ids = @(Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
           Where-Object { $_.CommandLine -like '*nlscope.py*' } |
           Select-Object -ExpandProperty ProcessId)
  $ps = if ($ids.Count -gt 0) { Get-Process -Id $ids -ErrorAction SilentlyContinue }
  if (-not $ps) {
    "{0:HH:mm:ss},-,-,-" -f (Get-Date) | Add-Content $log
  } else {
    $mb = [math]::Round((($ps | Measure-Object WorkingSet64 -Sum).Sum)/1MB,1)
    $h  = ($ps | Measure-Object HandleCount -Sum).Sum
    $t  = ($ps | ForEach-Object { $_.Threads.Count } | Measure-Object -Sum).Sum
    "{0:HH:mm:ss},{1},{2},{3}" -f (Get-Date), $mb, $h, $t | Add-Content $log
  }
  Start-Sleep -Seconds 30
}
```

先启动程序、确认标题是 `M6.0.0-rc2`，再开这个监控；程序没起时脚本记 `-` 而不是报错，可以先开监控再开程序。

## 3. `qdrop` / `stale` 的实测覆盖（当前条件不具备，未验证）

**状态（2026-11-15）**：用户反馈"屏蔽实验目前做不了"（手头没有能罩住两块板的金属盒/铝箔等）。本条**保持未验证**，不伪造数据，也不把"跑了但没触发"当成通过。

**目的**：这两个计数器是 M6 新加的，目前**一次都没有非零过**。断电复位会把 responder 队列直接清空，所以验不到；必须"断链但两块板都保持供电"。

**可选的三种触发途径**（按代价从低到高）：

1. **距离拉断**：把 responder 端接长 USB（3 m 普通线，8 m 需有源延长线），再把两板拉开到通断边界之外。不需要屏蔽物，但需要长线。
2. **金属盒/铝箔罩住两块板**（原方案）：保持供电、不拔线，罩 15–30 s。需要盒子或铝箔。
3. **固件调试钩子强制断开**：在 initiator 侧加一条 UART 调试命令（例如收到 `D` 就 `sle_disconnect`），只重编 initiator、只烧一块。它能覆盖 `stale`（断开时 responder 队列里还有未发出的 RSP，重连后 epoch 不匹配 → `stale++`），但**覆盖不了 `qdrop`**——断开期间 initiator 不再发 REQ，responder 队列不会继续涨。需要改代码 + Linux 编译，属"要不要为这个计数器加调试口"的取舍。

**结论**：`qdrop` 需要 RF 退化（重传堆积）才可能非零，当前没有可控手段；`stale` 可用途径 1 或 3。两者都记在 `docs/代码审查-2026-11-15.md` 与 M6 已知限制里，写明"未验证"，不再列为阻塞项。

**将来有条件时怎么做**：按途径 1 或 2 执行——采集 → 断开 15–30 s → 恢复 → 再采 30 s，导出到 `artifacts\logs\M6\cfg500_sumintegrity\shield`，通过标准是 `board_latest_sum` 出现 `qdrop>0` 或 `stale>0`、`to`/`gaps` 同步增加。

## 4. 决策记录与仍待你定的一件事

### 4.1 应用层 CRC：**暂不做**（2026-11-15 已定）

理由：SLE/BLE 链路层已有每包 CRC 与自动重传，单跳、40 B 帧下应用层 CRC 能挡的主要是"缓冲区拼帧错位"与"旧包残留"，而现有长度校验 + `cfg_id` 回显 + REQ 填充模式已覆盖大部分；M6 四个实际缺陷里没有一个能靠 CRC 发现。

记录：不做，也不改帧格式，协议停在 v0.3。**重新考虑的触发条件**（任一出现时再提）：① 接入第三方设备或换链路（BLE、UART 隧道）；② 出现"帧长正常但数值离谱"的偶发坏样本；③ 要做 24 小时以上无人值守采集。

留下的痕迹：`docs\代码审查-2026-11-15.md` 的 B1 条目保持"未做"，`docs\protocol.md` 不加 CRC 段——避免后来人以为"漏了"。

### 4.2 版本与 Latest（2026-11-15 更新）

`M6.0.0-rc1` 早于"固件继承误报"修复，用户决定跳过干净机验收后**重打为 `M6.0.0-rc2`**（`ef762b64…` / `fff92bc8…`）。
线上仍是 `vM6.0.0-rc1`（预发行），`vM5.0.9-rc5` 仍是 Latest——是否把线上换成 rc2、是否设 Latest，待用户定。
