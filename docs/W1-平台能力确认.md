## 2. 源码里挖到的坑（这些都改在了代码里）

1. **两块板会撞 MAC**。离线副本的 `sle_uart_server_adv.c` 把本机地址写死成 `01:02:03:04:05:06`；两块板同时用同一个地址，扫描/连接行为不可预期。VM 那份已经改成 `sle_get_local_addr()` + 全零回退，本项目用的是这个版本。
2. **`osal_msleep(1)` 不是 1ms，也不是 10ms，是 20ms**。实测 19.996ms → LiteOS tick = 20ms（50Hz）。想跑 100Hz 以上的检查节奏只能忙等（`osal_udelay`）——所以主循环默认 500µs 忙等，代价是占一个核的 CPU（优先级 28，协议栈任务仍可抢占）。
3. **打点本身有成本**。`uapi_tcxo_get_us()` 每次要关中断 + 做一次 64 位除法（RV32 上是软件除法），实测 **1.20µs**（`get_count` 0.75µs）。这个开销已经和 loopback 的 6µs 底噪同一量级：**测 µs 级差异时要打两次点就吃掉 2.4µs**，要么改用 `get_count` 事后换算，要么把两次打点的差值当常数从 RTT 里减掉。
4. **`t4 - t3` 不是"回程时延"**。`t3` 是 B 的时钟，`t4` 是 A 的时钟，两者差一个未知偏差 δ。方案文档原来写"同一时钟，精确可得"是错的：这个量只能看趋势/抖动，不能报绝对值。真正干净的是 `(t3-t2)`（B 内）和 `(t4-t1)`（A 内）。
5. **停等会被超时拖慢**。一次只有一包在途时，对端不回，发包速率就掉到 `1/timeout`（默认 50ms → 20Hz），统计分母会变小；报告里要写清这一点。
6. **log UART 和 console UART 是两套**。`CONFIG_LOG_UART=1 @921600` 是 log 模块的出口，`osal_printk` 走的是 console（UART0 @115200）。改波特率时别只改一个。

### 5.2 噪声底（`-Role loopback`，B 板单板自环，2026-11-06 08:26 起）

连续 **20400 包**（≈204s），**无重启、seq 严格连续（间隔恒为 1）、sent=recv**：

| 分位 | RTT（µs） |
|---|---|
| P50 | **6** |
| P90 | 7 |
| P99 | **8** |
| P99.9 | 11 |
| Max | 125（偶发任务抢占） |
| 丢包 / 重复 / 坏包 / 超时 | 0 / 0 / 0 / 0 |
| `bproc`(t3-t2) 均值 / 最大 | 1 / 119 |
| `dlt` 均值 / 最大 | 1 / 4 |

采集窗口内 845 条明细的分布：`5µs×3, 6µs×753, 7µs×75, 8µs×11, 9µs×2, 11µs×1`（89% 落在 6µs 整）。

**结论**

1. **插桩自身开销的下界是 6µs，P99 = 8µs**。这 6µs 的构成已知：两次 `get_us`（2×1.2µs）+ 组包 + 一次同步回调。它不含空口和协议栈调度，因此是**下界**，不是 W1 要报的"噪声底"。
2. 相对 ms 级空口 RTT，插桩有 **200–1000× 余量**，方案 §2.3 的判据在插桩层面轻松满足。
3. **真正的噪声底要看双板**：`t2`/`t4` 在协议栈回调用例里取，回调延迟（几十 µs 到 ms）会主导底噪。W1 报告以双板实测为准，本节值作为对照基线。
4. 顺带验证了看门狗修复：20400 包连续跑 204s 不重启（修复前 18.4s 必挂），喂狗点在 `linkscope_main.c` 的 `engine_loop` 内、tick+drain 之后。

### 5.3 双板空口 RTT 与吞吐上限（A=initiator，B=responder，2026-11-06 11:54 那轮）

完整落盘 375 秒 / 8274 条样本，期间自动扫过 5 个连接间隔档：

| 请求的间隔 | 实际生效 | `cfm`(写→确认) | RTT P50 | RTT P90 | 速率 |
|---|---|---|---|---|---|
| 0x06 = 0.75 ms | 3 ms（下限） | 18–19 ms | 23.97 ms | 47.7 ms | 36–37 /s |
| 0x18 = 3 ms | 3 ms | 16.4 ms | **23.95 ms** | 24.1 ms | **40–41 /s** |
| 0x30 = 6 ms | 6 ms | 31.8 ms | 47.95 ms | 53.9 ms | 20.4 /s |
| 0x40 = 8 ms | 8 ms | 42.1 ms | 63.95 ms | 71.9 ms | 15.2 /s |
| 0x64 = 12.5 ms | 12.5 ms | 65–67 ms | 99.96 ms | 112–125 ms | 9.6 /s |

**结论**

1. `RTT_p50 = max(8 × 间隔, 24 ms)`：6/8/12.5 ms 三档都是精确 8.0 倍（误差 <0.2%）；
   **实际生效的最小连接间隔是 3 ms**（0.75 ms 会被顶回 3 ms，`param updated` 仍回 6 slot，属于只报不生效）。
2. `cfm ≈ 2/3 RTT` → 时间花在"请求挤上去"，回程 notify 只占小头；`bproc`(t3-t2) 只有 **12 µs**，
   **B 端不是瓶颈**。
3. **停止等吞吐上限 ≈ 41 包/秒**。放开在途窗口到 8、发包率拉到 1000Hz 反而更差：
   RTT 涨到 168 ms、`to/dup` 各 430，吞吐仍只有 ~50/s → **流水线无效**（详见项目日志 P26）。
4. 因此 **100 Hz 采样在本 SDK 的 SSAP 写-通知路径上做不到**，R4 风险成立。
   W1/W2 的实测按 **40 Hz（3 ms 间隔）** 档定；100 Hz 要么走 SLE low latency 数据通道
   （官方 SDK 无任何可用样例），要么留到 W2 单独立项。

RSSI：连上时读一次，**-39 dBm**（两板相距 ~10 cm、无遮挡）。
