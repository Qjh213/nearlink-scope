# LinkScope 上手指南：从零复现一次链路测量

本文面向"刚接手这个仓库的人"：不读源码，也能在半天内跑通一次测量、看懂结果、判断这条星闪链路稳不稳，并把证据存成别人能复核的样子。

配套文档：`docs/M5-双串口工作台.md`（界面操作细节）、`tools/README.md`（PC 工具逐项说明）、`firmware/linkscope/README.md`（固件角色与 CSV 字段）、`docs/M5-实验矩阵与评分.md`（测什么、怎么评分）。

---

## 0. 先搞清楚这东西是什么

LinkScope 是**双端协作式**测量：两块烧了探针固件的 H3863 开发板，一块当发起端（initiator，接 COM3），一块当响应端（responder，接 COM4）。发起端按固定速率发 SLE Write Command，响应端原样回写；发起端用自己的单一时钟量 `t1 → t4`，得到 RTT。

所以：

- 它能回答"这两块板之间这条 SLE/BLE 应用链路，在当前参数下，时延分布和稳定性如何"。
- 它**不能**测量任意商用星闪设备，也不是空口抓包器——没有对端探针配合，就没有数据。
- RTT 只用一个时钟，是干净的主指标；`bproc_us`（对端处理耗时）用响应端时钟；`dlt_us` 跨两块板的时钟，含时钟偏差，只能看趋势。

## 2. 五分钟跑通（不改任何固件）

假设两块板已经分别烧好 initiator / responder 固件（现成的包在 `artifacts/firmware/`，见第 6 节）。

1. **接线**：两块板 USB 插 PC。设备管理器里确认两个 COM 口，本项目的惯例是 COM3 = initiator、COM4 = responder，但以实际枚举为准。
2. **关掉其它串口软件**：QCOM、串口助手等必须先关闭，串口是独占的。
3. **启动**：在仓库根目录执行 `python tools\nlscope.py`（或 `.venv\Scripts\python.exe tools\nlscope.py`）；也可以直接双击 `dist\LinkScope\LinkScope.exe`（2026-11-15 用同一份源码重建）。
4. **配置两端**：主窗口选分析端 COM3，打开"串口工作台"新建辅助终端选 COM4。两端都用 `115200 / 8N1 / 无流控 / DTR 关 / RTS 关`。
5. **开始**：点"全部开始"（先开辅助端，再开主分析端）。
6. **复位顺序（关键）**：**先复位 COM4（responder），再复位 COM3（initiator）**。反了或只复位一块，发起端会拿不到对端，或收到不完整签名。
7. **等签名**：COM3 会打印启动平台签名，随后出现 `measurement-ready`。只有签名完整，界面才开始计时、样本才进入统计；中途接入的 `S` 行会被计为"已忽略中途样本"，这是设计行为，不是丢数据。
8. **看数**：p50 / p90 / p99 / p99.9 / max、jitter，以及 timeout / duplicate / out-of-order / bad / drop。
9. **停与存**：到时点"全部停止"（冻结会话），再点"联合导出"，选一个证据目录。

跑通的最低验收：COM3 连续出现 `S,1`、`S,2`、`S,3`……且序号不跳；界面样本数在涨；`to/dup/ooo/bad/drop` 全 0。

## 3. 跑一次正式实验（矩阵里的一个 cfg）

正式轮不是"随便跑一下"，每轮要能自证。流程：

1. **确认两端固件与 cfg**：initiator 的 cfg 由编译期 `.config` 决定；responder 不区分 cfg，只回显。两端包的 SHA-256 必须记录（见第 6 节）。
2. **在界面选"预期实验"**：程序会把 role、link、cfg、payload、rate、window、timeout 与所选条件逐项比对，已出现的 MTU 必须 520、interval 必须 24。不匹配的样本不进统计，界面会直接列出期望值与实际值——**不要绕过这个检查**。
3. **开双串口 → 先复位 COM4 → 再复位 COM3 → 等 ready 开始计时**。按"开始串口"前可以点一次
   **"开始前检查"**：它会告诉你串口是否选对、辅助串口有没有和主串口撞车、签名行到了没有、签名与所选
   规格差在哪、固件是否登记、工作区能不能写。**只有"没选串口/同一个口开两次"会让它判 FAIL**，其余都是提醒。
4. **跑满规定时长**：矩阵默认单轮 180 s，每条件 2 轮；cfg513（250B）先跑 60 s 冒烟；60 Hz 档不预设稳定。
5. **停止 → 联合导出**到 `artifacts/logs/M5/cfgNNN_<描述>/runX`。导出完成弹窗会带一行 `自检：…`，
   并把完整结果写进 `run.json` 的 `evidence_checks`：`FAIL` 只表示证据自相矛盾（CSV 行数与样本数不符），
   `WARN` 表示某项缺失或需要人看一眼（序号缺口、坏行、板端没发 SUM、固件哈希没填、没有 `.raw`）。
   **看到 WARN 不是让你删证据，而是要在 README 里写明为什么可以接受。**
6. **写 README**：两端固件 SHA-256、PC 版本、实际距离/遮挡/朝向、开始与结束时间、本轮结论。
7. **更新账本**：`docs/M5-实验矩阵与评分.md` §8 的进度表 + `artifacts/logs/M5/manifest.csv`。

停止条件（出现即停该轮，保留失败日志，不许重跑覆盖）：断链、连续 timeout、bad/drop 增长。

## 4. 怎么测"星闪链路稳不稳"

稳定性不是看一个数，是看**同一条件下的分布形状和尾部**。方法：固定一切能固定的，拉长时间，看分布是否漂移。

### 4.1 长测协议

- 条件：cfg500 近距（0.5 m 量级），40 B / 40 Hz，window=1，timeout=50 ms，intv=24。
- 时长：**≥ 10 分钟**（cfg521 的正式记录是 859.7 s / 8,600 样本，可作为模板）。
  M6 起另有一条 **30 分钟长跑**要求：`seq` 是 uint16，40 Hz 下 **27.3 分钟**回绕一次
  （60 Hz 时 18.2 分钟），跑满 30 分钟才能覆盖"回绕前后序号仍然连续"和"界面内存/句柄不随时间涨"这两件事。
  回绕在 PC 端表现为 `pc_sequence.wraps` 加一，**不是** `gaps`，不要当成丢样。
  实际长跑记录：30 分钟那轮 72,068 样本 `wraps=1`（P172），104.7 分钟那轮 251,343 样本 `wraps=3`
  （P182）。后者的内存斜率是 **+1.3 MB/min**，按此外推 4 小时约 410 MB、8 小时约 750 MB——
  想做超过 4 小时的无人值守采集，先把会话样本改成溢写/环形缓冲，别靠堆内存。
- 期间不动板、不动线、不动 USB 口、不开关手机热点；记录环境温度/位置是否变化。
- 每 200 个样本板端会打一条 `# SUM`；结束时核对板端 SUM 与 PC 精确统计的样本数是否一致（板端可能滞后几十条，属正常）。

### 4.2 判读顺序（先硬性，后数值）

硬性项，任一不满足 → 本轮标记"不可评分"，先查证据再谈性能：

1. 平台签名完整，`measurement-ready` 出现过；
2. 序号 `seq` 连续，无 gap / duplicate / out-of-order；
3. `drop = 0`、`bad = 0`、无断链；
4. 两端日志无 `nmi / exception / panic / hardfault / reboot / watchdog`；
5. PC 与板端样本数差异仅来自板端 SUM 滞后。

数值项，与基线对比着看（cfg521 基线：p50 14.6 ms、p90 16.3、p99 18.5、max 30.8、jitter 1.4 ms、bproc 45 µs、全零错误）：

- p50 是否随时间漂移（前后半段各算一次 p50，差 >10% 就要记）；
- p99 / max 是否出现新的长尾；
- jitter 是否系统性变大；
- timeout 是否从 0 变成非 0。

注意：矩阵的评分阈值是"结果索引"，不是协议合格线；不要把当前基线自动当成达标线。

### 4.3 想比较多档配置

一次只改一个变量（payload 或 rate 或距离或干扰），其它固定；每档至少 2 轮；跨档比较前先确认 PC 版本与两端固件 SHA 一致，否则差异可能来自工具本身。这条在 `docs/M5-实验矩阵与评分.md` §8 里有专门提醒。

### 4.4 已建立的参考基线（2026-11-14，M5 收官）

同一套工具、同一代固件（PC `M5.0.9-rc5`、responder P139 `072ba2ba…`）下测得，可直接拿来对照：

| 条件 | n | p50 | p99 | `>25 ms` 尖峰 |
|---|---:|---:|---:|---:|
| clean 40 B / 10 Hz | 8,600 | 14.639 ms | 18.479 | 9 |
| clean 40 B / 25 Hz | 4,508 / 4,522 | 14.778 / 14.907 | 17.868 / 18.818 | 0 / 0 |
| clean 40 B / 60 Hz | 11,389 / 10,889 | 14.908 / 14.909 | 18.040 / 18.387 | 4 / 6 |
| clean 40 B / 40 Hz（结尾基线） | 7,219 / 7,693 | 14.698 / 15.158 | 19.257 / 17.508 | 5 / 1 |
| **2.4 GHz 空口饱和 + 40 B / 40 Hz** | 7,547 / 7,318 | 14.675 / 15.159 | **22.758 / 21.199** | **47 / 31** |

怎么看：

- **判"受扰与否"看 `>25 ms` 尖峰计数**：clean 各轮 0–9 个，饱和干扰 31–47 个，分离度 5–10 倍，比 p99 稳。
- p99 在 clean 与受扰之间只有约 1.9 ms 的最小间隙，而轮间波动可达 1.7 ms，**单独用 p99 判读偏弱**。
- 40 Hz 下 p50 存在约 14.7 / 15.16 ms 两个稳定档（轮内平稳、轮间跳变，成因待查），
  所以**跨轮比较中位数时必须按轮登记，不要两轮合并取均值**。
- 干扰条件必须先用下载速率证明空口被压满（≥3 MB/s）；手机热点播直播只有约 5% 占空比，压不动链路。

## 5. 指标怎么读

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `seq` | 发起端样本序号 | 连续性是最廉价的完整性检查 |
| `rtt_us` / p50 | 单时钟往返时延 | 主指标，看中位数与分布 |
| p99 / p99.9 / max | 尾部 | 抖动敏感业务看这里 |
| `jitter` | 相邻 RTT 差分绝对值的平均 | 稳定性 |
| `to` (timeout) | 50 ms 内未回 | 可靠性，出现即有价值 |
| `dup` / `ooo` | 重复 / 乱序 | 异常信号 |
| `bad` | 帧或校验异常 | 不可评分信号 |
| `drop` | 板端计数丢弃 | 采样完整性 |
| `loss_ppm` | `timeout/(recv+timeout)` | 丢包率 |
| `bproc_us` | 对端处理耗时（响应端时钟） | 判断耗时在链路上还是在对端 |
| `dlt_us` | 跨板时差 | 含时钟偏差，只看趋势，别当单向时延 |
| 平台签名 | role/link/cfg/payload/rate/window/timeout/mtu/interval | 每轮的身份证明 |
| `# SUM` | 板端对数直方图统计 | 与 PC 精确分位数有小差异，属正常 |

## 6. 证据存哪、怎么命名

```text
artifacts/logs/M5/
  manifest.csv                      # 计划表（cfg 定义）
  cfg521_rate10/run1/               # 一档一目录，一轮一子目录
    initiator_COM3.log  initiator_COM3.csv  initiator_COM3.json  initiator_COM3.md
    aux_COM4.log
    run.json                        # 环境与配置记录
    README.md                       # 人写的摘要（必填）
```

- 命名：`<MMDD>_cfg<NNN>_run<N>_<pass|fail>`，例如 `1114_cfg521_run1_pass`；冒烟用 `smoke`，失败用 `fail` 且保留不删。
- 每轮六件套：initiator 原始日志、responder 原始日志、PC 四类导出、`run.json`、README。
- README 必填：两端固件 SHA-256、PC 版本、实际距离/遮挡/朝向、开始与结束时间、时长与有效样本数、结论、异常。
- 固件包本身放 `artifacts/firmware/`（`.gitignore` 已忽略 `*.fwpkg`），并在 `SHA256SUMS.txt` 登记；实验日志目录也不入库（见 `docs/提交与仓库规范.md`）。

**拿到别人的证据怎么验**：不用装环境、不用接线，一条命令：

```powershell
.venv\Scripts\python.exe tools\nlscope.py --reproduce artifacts\logs\M6\cfg500_sumintegrity\smoke
```

它只读那个目录，报告写到 `out\reproduce\<目录名>-reproduce.md`，内容包括：日志的 SHA-256、当时的程序版本与
`git_head`、双端固件 SHA-256、**记录值与本次重放逐项对照**（`n/p50/p90/p99/max`，会直接写"一致"或
"不一致（差 N）"）、板端计数器、自检结论，以及"这份数据能算出什么、不能算出什么"（统计能力分级）。
报告里出现"不一致"先看是不是分位数口径变了（M6 改了线性插值），再看是不是证据本身有问题。

**换个工具采的数据**：写一个 JSON 描述列名映射，就能把外部 CSV 读进来再走同一条导出链路：

```powershell
.venv\Scripts\python.exe tools\nlscope.py --import-csv foreign.csv --adapter adapter.json --export out\imported
```

适配器必需 `seq`/`t1_us`/`t4_us` 三列映射，缺了会直接报错（不会替你补零）；`time_scale` 用来把毫秒换成
微秒（填 1000）；坏行会按异常类型计数并打印"读 N 行 / 导入 M 条 / 坏行 K"。

## 7. 出问题怎么办

| 现象 | 常见原因 | 处理 |
|---|---|---|
| 打开串口失败 | QCOM/串口助手没关；DTR/RTS 被别的软件拉高 | 关掉其它软件，确认 DTR/RTS 关 |
| 一直没签名 / 不计时 | 复位顺序错；只复位了一块；固件是 monitor/loopback 角色 | 先复位 COM4 再复位 COM3；核对固件角色 |
| 有 `S` 行但样本不涨 | 中途接入，签名不完整（严格准入） | 重新按顺序复位，不要停/开串口代替复位 |
| 乱码 | 波特率不是 115200；线材问题 | 统一 115200/8N1/无流控 |
| 样本中途断了 | 板子重启、USB 松动、看门狗 | 保留日志，查两端有没有 `nmi/exception/reboot` |
| 采样中按了板卡复位 | 板子重新上电，断链要等 SLE 监督超时（约 32 s）才会重连 | **这一轮作废重跑**：复位期间约 30 s 没有样本，混在一起会让 `n` 与板端跨度失真。导出的 `run.json` 会写 `board_restarts > 0`，自检给 `sequence=warn 板卡重启 N 次`。想要“复位后继续”就当新的一轮：先停止、再开始串口 |
| 串口从下拉框消失 | 拔线/整板断电导致 CH340 重枚举，程序不会自动重连 | 插回后在“开始串口”重新打开（新会话），旧数据先导出 |
| 两轮差异很大 | 环境变了（距离/干扰/供电）或 PC 版本不同 | 先对照 README 与环境记录，再决定是否重跑 |

## 8. 要改固件或换 cfg 时

1. 在 Windows 仓库里改 `firmware/linkscope/` 源码；
2. 用 `firmware\scripts\sync-to-sdk.ps1` 同步源码并改 SDK 的 `.config`：`-Role initiator -Link sle -SleWriteMode command -CfgId 522 -Hz 25 -Payload 40 -Window 1 -TimeoutMs 50 -IntvSlot 24`；
3. 在 Ubuntu 里构建：`python3 build.py -c ws63-liteos-app`，产物 `output/ws63/fwpkg/ws63-liteos-app/ws63-liteos-app_all.fwpkg`；
4. 回 Windows 用 BurnTool（921600）烧录，点烧录后几秒内给板子上电；
5. 归档产物到 `artifacts/firmware/`，算 SHA-256，必要时 `strings` 确认包内 role/cfg；
6. 把 SHA 写进本轮 README 和 `docs\项目日志.md`。

注意：`sync-to-sdk.ps1` 每次都会覆盖 SDK 里的 `ws63_liteos_app.config.bak.linkscope`。切换前先手工另存一份带日期和用途的备份，否则上一档配置就没了。

## 9. 一个阶段"算完成"的四个条件

矩阵里的实验数据齐了，不等于这个阶段能做交付。按 `docs\接管计划.md` §10，一个 M 阶段必须四件都齐：

| # | 交付物 | 检查方式 |
|---|---|---|
| 1 | 代码 | 测试全绿（`python -m unittest discover -s tests` + `python tools\test_nlscope.py`），提交干净 |
| 2 | 原始证据 | `artifacts/logs/M5/` 下每轮六件套 + README，`run.json` 能自证固件身份 |
| 3 | 项目日志 | `docs\项目日志.md` 有对应的 Pnnn 条目，写清口径与例外 |
| 4 | 阶段文章 | 一篇 CSDN 风格的文章，正文与配图存到 `E:\Starklink\文章\link\M<n>\` |

第 4 条容易被漏掉——它是"项目交付"而不是"实验完成"的标记。文章要求：个人开发笔记口吻、区分代码事实/实测结果/解释/未验证推断、配图带 `.svg` 源文件、发布后在项目日志记录标题、链接和对应提交。

M5 的文章是 `E:\Starklink\文章\link\M5\LinkScope-M5-从10Hz到60Hz-我怎么判断星闪链路稳不稳.md`，四张图分别是封面、证据链、速率分位数、受扰对照。
