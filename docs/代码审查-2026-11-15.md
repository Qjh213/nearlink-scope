## 2. P0 · 会让证据说谎

### P0-1 `ooo`（乱序）恒为 0
- 位置：`firmware/linkscope/linkscope_main.c:157-162`（SUM 字段表）、`tools/nlscope_core.py:335-336`（`counters.get(key, 0)`）
- 现象：固件 SUM 只有 `sent/recv/to/dup/bad/drop`，没有 `ooo`；PC 侧补 0 后照常输出 `"ooo": 0`。
- 影响：报告里“乱序 0”无法证明任何事；`docs/M6-程序改进与第三方接入.md:10` 声称“当前程序可以直接完成……乱序……”，与实现冲突。
- 建议：固件 SUM 增加 `ooo`（initiator 记录 `seq < last_seq` 且不在重传窗口内的事务）；PC 侧对缺失字段输出 `None`/`—`，不要默认 0。
- 验收：`python -c "import json,glob;d=json.load(open(glob.glob('artifacts/logs/M5/cfg522_rate25/run1/initiator_COM3.json')[0]));print(sorted(d['board_latest_sum']))"`（板端 SUM 在 `initiator_COM3.json`，不在 `run.json`）应包含 `ooo`；缺失时可看到 `—`。

### P0-2 SUM 行缺失时静默变成“全零错误”
- 位置：`tools/nlscope_core.py:335-336`
- 现象：串口少收一行 `# SUM`（60 Hz 下完全可能），`to/dup/bad/drop/loss_ppm` 全部取默认 0。
- 影响：最危险的一类假阴性——丢包现场被打印成“零错误”。
- 建议：区分“没有 SUM”和“SUM 全零”；`run.json` 里加 `sum_frames_seen`，为 0 时报告显式标注“未收到板端计数器”。
- 验收：构造一份缺 SUM 的日志回放，报告必须出现“未收到 SUM”字样。

### P0-3 板端接收队列丢帧从不打印
- 位置：`firmware/linkscope/linkscope_main.c:92`、`:101`、`:107`（`g_rx_drop` 自增处），SUM 在 `:157-162`
- 现象：`g_rx_drop` 有自增，但 SUM 只打 `drop=ring_drop`，`rx_drop` 既不进 SUM 也不进诊断行。
- 影响：板子主循环卡顿导致响应被丢，**任何导出里都看不到**。
- 建议：SUM 增加 `rx_drop`，或把它并入 `drop`，并在 `docs/M5-实验矩阵与评分.md` 注明口径。
- 验收：制造一次队列溢出（压测），SUM 中 `rx_drop` 非 0。

### P0-4 发送失败与写确认失败不计入任何计数器
- 位置：`firmware/linkscope/engine.c:268`、`:280`（`send_err`）；`firmware/linkscope/link_sle_initiator.c:261-264`（write-cfm 失败直接 `return`）
- 影响：链路层发不出去时，既不算 `bad` 也不算 `to`，`loss_ppm` 的分母（`recv+timeout`）也把它排除 → 统计仍然“干净”。
- 建议：`send_err` 入 SUM；write-cfm 失败计入 `bad`（或独立 `cfm_err`），并在报告里单列。
- 验收：断链后强制发送，SUM 出现非零 `send_err`。

### P0-5 CSV 回放静默丢行，且不校验固件不变量
- 位置：`tools/nlscope_core.py:496`（`except (KeyError, TypeError, ValueError): continue`）、`tools/nlscope_core.py:476-509`（`load_csv`）；对照 `tools/nlscope_core.py:151-156`（实时路径的不变量检查）
- 影响：同一份数据“走原始日志”和“走 CSV”得到不同可信度；外部复算恰恰都走 CSV。
- 建议：`load_csv` 复用同一套不变量、统计 `rows_skipped` 并在报告里打印；跳过超过阈值时拒绝导出。
- 验收：喂一份含 3 行坏数据的 CSV，报告中 `rows_skipped=3`。

### P0-6 导出可以静默覆盖既有证据
- 位置：`tools/nlscope_core.py:364-388`（`write_text` 四个文件）、`tools/serial_terminal.py:404-406`（辅助窗口 `write_log`）
- 影响：同一目录再导一次就覆盖上一轮，与“不覆盖实验数据”的红线直接冲突。
- 建议：导出前检测同名文件，存在则拒绝（或自动加 `-2` 后缀并在报告里注明）；辅助窗口改为与 `save_log` 一致的另存对话框。
- 验收：同一目录连续导出两次，第二次必须报错或改名，原文件哈希不变。

### P0-7 辅助端的“原始日志”不是原始字节
- 位置：`tools/serial_terminal.py:131`（`decode("utf-8", errors="replace")`）、`:471-484`（渲染+时间戳前缀）、`:508-517`（保存）与 `:404-406`
- 现象：保存的是**渲染后的文本**，不是收到的字节。非 UTF-8 字节变成 U+FFFD；跨块的多字节字符会被劈成两个 U+FFFD；块尾没有换行时会补一个 `\n`（`serial_terminal.py:482-483`），于是原始行边界被改写。
- 影响：声称的“原始终端只搬字节”在落盘环节不成立；QCOM 的 `<0D><0D><0A>` 这类痕迹不会保留，字节级取证无法进行。
- 建议：raw 日志单独保留**原始字节流**（`LogSink` 直写），界面渲染只用于显示；或另存一份 `.bin`/`.raw`。
- 验收：发送一段含 `0x00/0xFF` 与裸 CR 的数据，保存的 `.txt` 里应能还原原始字节（或同时存在 `.raw`）。

### P0-8 主分析与辅助端都用 `errors="replace"`，坏行不计数
- 位置：`tools/nlscope.py:716`、`tools/nlscope.py:1016`、`tools/nlscope_core.py:159-160`（`except ValueError: pass`）
- 影响：串口乱码变成 U+FFFD 后解析失败，PC 侧没有任何“坏行/坏帧”指标，只有一个来自板端的 `bad`（且板端 `bad` 语义还混着队列满，见 P3-2）。
- 建议：`LineParser` 增加 `parse_failures`（按 `S,`/`# SUM`/`ADV` 分类），写入 `run.json` 并在报告里显示。
- 验收：喂 10 行损坏的 `S,` 行，`run.json` 出现 `parse_failures=10`。

### P0-9 `run.json` 不含代码与固件身份
- 位置：`tools/nlscope.py:423-434`（`run.json` 字段）、`tools/nlscope.py:20`（`APP_VERSION` 手工常量）
- 现象：没有 git SHA、没有 dirty 标记、没有固件包 SHA，只有手写的 `app_version`。
- 影响：P148 记录的“早期轮次无法自证固件身份”没有被程序化堵住；改了代码不升版本也看不出来。
- 建议：`run.json` 增加 `git_head`、`git_dirty`、`firmware_sha256`（从 aux 日志首行的版本串匹配或用户手填），并写进报告。
- 验收：导出后 `run.json` 中三项齐全；有未提交改动时 `git_dirty=true`。

## 3. P1 · 数值口径与长跑

### P1-1 `percentile()` 是“最近秩”，不是线性插值
- 位置：`tools/nlscope_core.py:236` `int(round((n-1)*p))`
- 影响：cfg521 p99.9 = 24670（JSON）vs 24933（CSV 独立复算），此前只能人工解释；报告却写着“精确统计”。
- 建议：改为 `(n-1)*p` 线性插值，或在报告里显式写“最近秩口径”。**两选一，但必须写清楚。**
- 验收：与 numpy 默认 `percentile` 对齐（误差 < 1 µs）或文档注明差异。

### P1-2 板端分位数有 ~6% 量化误差，但报告没标
- 位置：`firmware/linkscope/stats.h:6`
- 实测：cfg522 run1 板端 `p99=18325` vs PC 精确 `17868`（差 2.5%，落在 6% 预期内）。
- 建议：报告把板端分位数标注为“板端直方图估计（最坏 ±6%）”，或干脆只展示 PC 精确值。
- 验收：报告文本中出现该限定语。

### P1-3 `_ints()` 用 `int(x, 0)`，且 `split("/")[0]` 截断
- 位置：`tools/nlscope_core.py:128`
- 现象：前导 0 按八进制（`"050"`→40）；`"08"` 抛错后被 `continue` 静默吞；`bproc=%u/%u` 只取前半，`bproc_max`、`dlt` 的 max 在每个 JSON 的 `board_latest_sum` 里都丢了。
- 建议：`int(x, 10)`；斜杠字段分别解析并存成两项。
- 验收：回放含 `bproc=41/77` 的 SUM，JSON 出现 `bproc_max=77`。

### P1-4 `dlt` 负数直接归零
- 位置：`firmware/linkscope/engine.c:147`
- 影响：时钟偏差为负的样本全被塞进 0 桶，`dlt` 分位数系统性偏低；“归零”与“真 0”不可区分。
- 建议：负值单独计数（`dlt_neg`），或保留有符号字段。注释已解释动机，但不应牺牲可辨识性。
- 验收：SUM/PC JSON 中出现 `dlt_neg` 计数。

### P1-5 `sample_span_s` 用 PC 墙钟
- 位置：`tools/nlscope_core.py:339-343`
- 影响：跨机、跨天对比时长有偏差；PC 卡顿一次就把跨度拉长。
- 建议：同时记录板端跨度（`t4_last - t4_first`，模 2^32 处理回绕），报告以板端为准、墙钟为辅。
- 验收：两轮时长与板端样本数/速率一致。

### P1-6 `seq` 是 uint16，60 Hz 下 18.2 分钟回绕
- 位置：`firmware/linkscope/engine.c:259`（`e->seq++`），字段类型见 `firmware/linkscope/engine.h`
- 计算：65536/60 ≈ 1092 s（18.2 min）；40 Hz ≈ 27.3 min；10 Hz ≈ 109 min。
- 影响：M6 的“≥2 小时”长测必然多次回绕；PC 侧目前不做任何 seq 连续性检查，事后审计会把 `65535→0` 当乱序/复位。
- 建议：PC 侧按 uint16 回绕感知计算连续性，`run.json` 记录 `seq_wraps`；或固件改 uint32（需同步改协议与解析）。
- 验收：跑 25 分钟 @60 Hz，`run.json` 的 `seq_wraps=1` 且连续性报告无乱序。

### P1-7 全量数据只在内存，崩溃即失
- 位置：`tools/nlscope_core.py:243-247`（`Session` 存 `raw_lines/samples`）、`tools/serial_terminal.py:352`、`:484`（`log_lines`）
- 现状：只有点“导出”才落盘；`LogSink`（`serial_reader.py:88-116`）本可增量写，但主路径没用。
- 影响：一次断电/崩溃 = 整轮证据全丢。
- 建议：主会话与辅助端都接 `LogSink`，每 N 行或每 2 s flush 一次；导出时再生成聚合文件。
- 验收：采集中直接 kill 进程，磁盘上应有截至最后一秒的原始行。

### P1-8 Tk 文本框无行数上限
- 位置：`tools/serial_terminal.py:471-488`（每次 `insert`，从不清理）
- 对比：QCOM 在 4999 行时整体清屏（行为规格 §3）。
- 影响：60 Hz 跑 10 分钟，原始终端明显变卡。
- 建议：沿用“显示窗口滚动淘汰”（保留最近 N 行，原始数据仍在 `log_lines`/`LogSink`）。
- 验收：连续 10 分钟采集，UI 输入响应无明显延迟。

### P1-9 每次重绘都全量重算
- 位置：`tools/nlscope.py:821-837`（`draw()` 里 `metrics()` + `histogram` + CDF），由 `poll()` 以 100 ms 节奏触发（`nlscope.py:180`、`:762`）
- 说明：**是按 100 ms 批量算，不是每条样本算**——这点比初判轻。但 60 Hz 跑 1 小时后，每 100 ms 对 20 万样本排序仍然浪费。
- 建议：增量维护均值/直方图，分位数按需（导出时）计算。
- 验收：60 Hz 采集 30 分钟，主线程 CPU 占用下降且曲线不卡。

## 4. P2 · 可靠性与交互

### P2-1 `dropped_bytes` 是死计数器
- 位置：`serial_reader.py:29`；全仓无 `+=`。
- 建议：在 `feed()` 超限丢弃、`_flush_pending()` 溢出两处真实累加；或删除该字段。

### P2-2 `forced_flushes` 语义混用
- 位置：`serial_reader.py:57`（超 `max_pending` 强刷）与 `:78`（空闲冲刷）都 `+= 1`。
- 建议：拆成 `forced_flushes` 与 `idle_flushes`。

### P2-3 `SerialReader` 生产代码未使用
- 位置：`serial_reader.py:119`；仅 `tests/test_splitter.py` 引用；生产走 `tools/serial_terminal.py:59` 的 `pump_serial_lines`。
- 影响：13 项测试里有一部分在验证一条生产不走的路径，验收 8 条给的是假安全感。
- 建议：二选一——生产切到 `SerialReader`，或把 `pump_serial_lines` 抽成同一实现并补测试。

### P2-4 主串口打开没有 `exclusive=True`
- 位置：`tools/nlscope.py:641-651` vs `serial_reader.py:156`
- 影响：两个程序可同时打开同一端口（CH340 行为依赖驱动），与“独占”口径不符。
- 建议：主路径补 `exclusive=True`，失败时给出明确提示。

### P2-5 串口异常后不重连
- 位置：`tools/nlscope.py:675-681`（异常入队）、`:705-706`（只显示一次错误）
- 建议：提供“自动重连”开关（默认关，避免污染证据），或至少在状态栏提示“需要重新开始”。

### P2-6 `errors=None` 时异常静默
- 位置：`serial_reader.py:173-175`
- 建议：`errors` 缺省时至少 `logging.exception`，不允许完全静默。

### P2-7 boot 门只认硬编码文案且无超时
- 位置：`tools/serial_terminal.py:77-83`（`boot\.` 结尾正则）

## 5. P3 · 固件

### P3-1 探针帧没有 CRC
- 位置：`firmware/linkscope/probe.c:56-68`；只校验 magic + type。
- 影响：比特翻转若恰好保住这两字节，会被当成有效样本（PC 的 `rtt` 不变量只能挡一部分）。
- 建议：加 1 字节 CRC-8 或 16 位累加和；同步改 `tools/nlscope_core.py:151-156` 的不变量。

### P3-2 responder 队列深度 5，满即计 `bad`
- 位置：`firmware/linkscope/link_sle_responder.c:22`（深度）、`:82-85`（满时 `g_dbg_bad++`）
- 影响：60 Hz 下只有 ~83 ms 余量；把“来不及处理”误标成“帧坏”，污染 `bad` 语义。
- 建议：队列满单独计数（`q_drop`），`bad` 只表示解析失败；或加深队列并测最坏处理时间。

### P3-3 断链后队列里的旧 RSP 不清理
- 位置：`firmware/linkscope/link_sle_responder.c:176-181`
- 影响：重连后可能回一批过期包（initiator 侧记 dup，不污染 RTT，但干扰判定）。
- 建议：DISC 时清空队列。

### P3-4 responder 不回显校验 `cfg_id`
- 位置：`firmware/linkscope/link_sle_responder.c`（`resp_write_cb`）
- 影响：混板/烧错固件时没有任何告警。
- 建议：`cfg_id` 不匹配时回错误码并计数。

### P3-5 `write_cfm` 只在 Write Request 模式编译，但日志仍打 `cfm_n=0`
- 位置：`firmware/linkscope/link_sle_initiator.c:254-280`（`#if` 包裹）、`firmware/linkscope/linkscope_main.c:239-247`（每 5 s 打印）
- 影响：正式配置是 Write Command，`cfm_n=0` 是必然值，日志里容易被误读成“写确认全失败”。
- 建议：该模式下不打印 `cfm_n`，或标注“N/A”。

### P3-6 辅助窗口日志不自动落盘
- 位置：`tools/serial_terminal.py:404-406`、`:508-517`（仅手动保存）
- 建议：与 P1-7 合并解决（增量写）。

### P3-7 时间戳按块前缀，不是按行事件
- 位置：`tools/serial_terminal.py:471-484`
- 现象：一行被拆到两个块时，两段都会带时间戳前缀，日志里出现“半行 + 时间戳 + 半行”。
- 建议：前缀只在行首插入（用 splitter 的整行语义），半行不带前缀。

### P3-8 探针 payload 不校验内容
- 位置：`firmware/linkscope/probe.c:88-90`（seq 填充）
- 影响：回包内容被改也不会被发现（只能靠 RTT 不变量间接发现）。
- 建议：payload 内嵌 seq + 校验字节，initiator 校验回显一致。

## 6. 不建议改的（设计取舍，先决策）

1. **`jitter` 用相邻差分平均，不是标准差**——`tools/nlscope_core.py:331`，文档已注明，跨项目对比时注意即可。
2. **`dlt` 只作趋势**——跨板时钟本就不可比，别为它加精密同步。
3. **停止后清空数据**——`nlscope.py:623` 注释说明是有意为之；只需改文案（P2-8），不要改成“继续”。
4. **回放 CSV 时不重算 RTT**——CSV 是导出产物，重算会掩盖导出错误；保持“只校验、不修正”。
5. **`sample_span_s` 用墙钟**——若板端时钟不可靠，墙钟反而是唯一可用的；P1-5 的建议是“双记”，不是替换。
