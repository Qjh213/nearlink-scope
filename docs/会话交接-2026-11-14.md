## 2. 当前阻塞故障与证据

M5 cfg521（SLE Write Command、40 B、10 Hz、window=1、timeout=50 ms、intv=24）冒烟时：

- PC 主窗口完整识别 `role=initiator`、`cfg=521`、`ready=yes`；
- COM3 原始终端完整显示启动、连接、MTU、属性发现、参数更新和第一条 `S,1,...`；
- 此后 COM3 不再产生 `S` 样本；
- COM4 心跳中的 `req/rsp` 仍从 63 持续增长到 191，`bad=0`、`lasterr=0`。

因此不能再把问题归因于 PC 窗口“没有显示日志”。PC 已经收到并展示第一条样本；当前核心现象是：
响应端认为 notification 提交成功，但发起端只收到第一包。

### 已做但不足的 P134

提交 `5345768` 把 initiator 的 SSAP 回调改成 SPSC 接收队列，使 engine 的 inflight、统计和样本环只由
LinkScope 任务修改，消除了回调与任务并发访问 engine 的数据竞争。实机仍然只有 `S,1`，说明这是正确的
并发加固，但不是当前故障的充分根因。不要回退它。

### 待验证的 P135

提交 `307ebdb` 修改 responder：旧代码在 SSAP write callback 内直接调用
`ssaps_notify_indicate()`。API 返回成功只说明调用被接受，不能证明客户端收到；旧代码却立即增加 `rsp`。
新代码改为：

```text
SSAP write callback
  → 记录 t2、解析 REQ
  → 非阻塞写入 responder 消息队列
  → responder 任务取出事件
  → 记录 t3、构造 RSP
  → 调用 notification API
```

这避免在 SSAP service 回调内部重入 SSAP 发送路径。该修复已经同步到 SDK，但截至交接时尚未完成 Ubuntu
构建、COM4 烧录和实机验收，所以它是“待验证假设”，不能在文档或文章里写成已解决。

如果 P135 后仍只有一条样本，下一步必须先增加可区分的证据，不要继续猜：

- responder：分别统计 `REQ callback`、`queue enqueue`、`queue dequeue`、`notify API success/fail`；
- initiator：统计 notification callback 实际触发次数；
- 每秒在任务上下文打印一次计数，不在协议栈回调里打印；
- 用四组计数确定丢失发生在队列前、通知提交、协议栈交付还是 initiator 回调。

## 6. PC 工具使用约束

- 主分析端：COM3；响应端：COM4；115200/8N1/无流控，DTR/RTS 关闭；
- 必须关闭 QCOM，避免串口独占冲突；
- 使用程序内“串口工作台”同时打开 COM3/COM4；
- 点击“全部开始”视为新会话，旧日志不回填；随后必须重新复位两块板；
- 只有捕获完整 `boot.` 和完整平台签名后才允许正式采集；
- COM3 原始终端与主解析器共享同一个串口句柄，不应再次打开 COM3；
- 辅助终端可开多个，但每个 COM 端口只能被一个窗口占用；
- 当前 PC 两个 Python 进程是虚拟环境启动器与实际解释器的父子结构，不代表两个程序抢串口。

开发启动：

```powershell

.\.venv\Scripts\python tools\nlscope.py
```

## 8. 项目边界与写作规则

- LinkScope 是双端探针协作式应用链路测量工具，不是空口抓包器；
- RTT 只用 initiator 单板时钟计算；`t3-t2`只表示 responder 本地处理；跨板时间戳差不能称为单向时延；
- 结论必须限定为当前 H3863、SDK、固件、参数和现场环境；
- 不写无来源的 SLE 速率、时延或功耗宣传数字；
- 每个 M 阶段完成后写一篇 CSDN 进度文章，采用个人学习/开发笔记口吻；
- 文章与配图保存到 `E:\Starklink\文章\link\M1` 至 `M6` 对应目录；未经用户确认不直接发布。
