## 0. 一页摘要

LinkScope 想做的是一台**星闪（NearLink / SLE）链路的无线示波器**：两块开发板各自插在电脑上，跑一段探针固件，实时画出两台设备之间的**往返时延（RTT）分布**，而不是只给一个平均值。

已经做到的事：

- 两块 BearPi-Pico Hi3863（WS63 芯片）之间跑通 SLE 连接，**40 Hz、40 字节载荷、连续 3 分钟零丢包**，RTT **p50 = 23.9 ms、p99 = 27.0 ms**，三段采样之间 p50 差 2 µs。
- 把这 24 ms 拆开看：**RTT ≈ max(8 × 连接间隔, 24 ms)**，连接间隔从 12.5 ms 扫到 0.75 ms，实测**最小生效间隔是 3 ms**，吞吐**上限约 41 包/秒**。
- 因此判定：**这台芯片 + 这套 SDK 上做不到 100 Hz 双向 RTT**。要么降到 40 Hz 出可信数据，要么换测法（见 §6）。
- 顺手量了仪器自身的时基与噪声底：微秒时钟 40 ticks/µs、取一次时间戳 1.20 µs、单板自环 p50 = 6 µs。也就是说**测量噪声比被测信号小三个数量级**，数据是可信的。

还没做到的事：

- **波形界面没写**（现在只吐 CSV 文本）。
- **BLE 对照没跑**（代码刚写完，未编译验证）。
- **只能测跑我们固件的两块板**，"拿它去测任意星闪设备"目前不成立（见 §5.3）。

一句话判断：**测量内核成立且数据可信；"通用星闪示波器"这个定位不成立；产品的价值在"可信的分布 + 可复现的对比"，不在"通用"。**

## 1. 项目要解决什么问题

### 1.1 问题

星闪（SLE）开发者想知道"这条链路到底快不快、稳不稳"，现在能拿到的只有：

- 厂商给的吞吐/时延**标称值**（"低时延"到底多低？）；
- 自己写个 demo 打日志，测出来的数字**不知道自己信不信**（串口打印本身就有毫秒级开销）。

缺的是**仪器**：能告诉开发者"在这套配置下，RTT 的分布长什么样、尖峰多高、丢包多少、换一个参数会变多少"。

### 1.2 目标（可验收）

1. 两块板之间测 RTT，给出**分布**（p50/p90/p99/p99.9/max）而不是均值。
2. 数据**可复现**：同配置重跑，分位数差 < 1%。
3. 能回答"慢在哪一段"：总往返、对端处理耗时、发送确认耗时分别给出。
4. 同板 **BLE 对照**：同样的测量代码换传输层，看协议差异带来的差别。

### 1.3 非目标（明确不做）

- 不做单向时延（两块板晶振不同步，见 §6.2）。
- 不做协议解析/抓包（不是 sniffer）。
- 不承诺"测任意星闪设备"（见 §5.3）。

## 2. 硬件与工具链

| 项 | 内容 |
| --- | --- |
| 开发板 | BearPi-Pico Hi3863 × 2（WS63 芯片，RISC-V，SLE + BLE + WiFi） |
| SDK | HiSilicon WS63 SDK（厂商全量源码树，约 1.5 GB） |
| 构建 | **只能在 Ubuntu 20.04 虚拟机里**（Linux 工具链；Windows 版工具链缺 DLL） |
| 构建命令 | `python3 build.py -c ws63-liteos-app`，产物 `output/ws63/fwpkg/ws63-liteos-app/ws63-liteos-app_all.fwpkg` |
| 烧录 | BurnTool（Windows），921600 波特率，选 `_all.fwpkg`，点烧录后几秒内给板子上电 |
| 串口 | QCOM（Windows），115200，可开"保存日志"落盘 |
| 主机侧开发 | Windows + PowerShell 7；固件源码在工作区，用脚本单向同步进 SDK 树 |

**一个环境事实**：虚拟机磁盘通过 RaiDrive 的 SFTP 映射成 `Z:` 盘，Windows 侧直接读写 `Z:` 就等价于操作虚拟机磁盘。虚拟机看不见 Windows 的盘（VMware 没配共享文件夹），所以 `Z:` 是唯一通道。这条链路今天断过两次（虚拟机网卡被断开），是工程风险之一。

**为什么不在 Windows 编译**：SDK 的构建链是 cmake/make/bash + RISC-V Linux 工具链，Windows 上跑不起来。所以流程是「Windows 改码 → 同步到 Z: → 虚拟机编译 → Windows 烧录」。

## 3. 系统架构

### 3.1 分层

```
┌──────────────────────────────────────────────┐
│ 上位机（Windows/PC）                          │  ← 只显示、只配置，**不参与计时**
│   串口读 CSV → 波形 / 直方图 / 分位线          │      （USB 串口有毫秒级迟滞）
└───────────────────┬──────────────────────────┘
                    │ USB 串口（115200，文本 CSV）
┌───────────────────┴──────────────────────────┐
│ 探针固件（两块板，同一份代码，编译期选角色）    │
│  ┌────────────────────────────────────────┐  │
│  │ linkscope_main.c  角色分派 / 上报        │  │
│  ├────────────────────────────────────────┤  │
│  │ engine.c   停等引擎 + 在途窗口 + 超时    │  │
│  ├────────────────────────────────────────┤  │
│  │ probe.c    帧编解码（12B REQ / 20B RSP） │  │
│  │ stats.c    对数分桶直方图 + 分位数       │  │
│  ├────────────────────────────────────────┤  │
│  │ link_ops.h  传输层抽象                  │  │
│  │   ├─ link_sle_*.c    （已实现、已实测）  │  │
│  │   ├─ link_ble_*.c    （刚写完、未验证）  │  │
│  │   └─ link_loopback.c （单板自环）        │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

关键设计：**传输层抽象只有 4 个函数**（`start / send / ready / poll`），上层协议、引擎、统计对 SLE 和 BLE 完全共用。这样"同板 BLE 对照"才是干净的对照——变量只有一个。

### 3.2 时序与测量定义

一次测量（A = 发起端，B = 响应端）：

```
A: t1 发出 REQ ──────────────► B: t2 收到，立刻组 RSP，t3 发出
A: t4 收到 RSP ◄──────────────┘
RTT = t4 - t1              （同一块板的时钟，可信）
对端处理 = t3 - t2         （B 自己的时钟，可信）
```

**只有 `t4-t1` 和 `t3-t2` 是两个可信量。** `t4-t3`（回程）跨两块板、晶振不同步，差值里含未知的时钟偏移 δ，**不可解释**——这一点在文档里反复强调，避免别人拿它当"下行时延"用。

### 3.3 帧格式（小端）

```
REQ (A→B)  12 字节头 + 填充，默认 40 字节
+0 magic 0xA5 | +1 type 0x01 | +2 seq u16 | +4 t1_us u32 | +8 cfg_id u32

RSP (B→A)  固定 20 字节
+0 magic 0xA5 | +1 type 0x02 | +2 seq u16 | +4 t1_us u32 (回显)
+8 t2_us u32 | +12 t3_us u32 | +16 cfg_id u32 (回显)
```

`t2/t3` 由 B 端在**收到回调的第一行**和**发出前的最后一行**取，中间只做组帧。

### 3.4 引擎

- 默认**停等**（window = 1）：发一包、等在途清零再发下一包。
- 支持窗口 1–8（做过实验，见 §4.4，结论是无用）。
- 超时（默认 50 ms）、坏帧、重复、乱序**分开计数**，不混成一个"丢包率"。
- 热路径（收包回调）**不打印、不 malloc**；打印全在任务上下文，避免串口把测量带歪。

## 4. 已经发生的事实（W1 三个实验）

### 4.1 实验一：时基与调度标定（单板，role=timing）

| 项 | 实测 | 说明 |
| --- | --- | --- |
| ticks/µs | **40**（头文件宏写的是 24） | 用串口墙钟交叉验证：50 次 `osal_msleep(1)` 实测 999.8 ms 对 1000 ms，误差 < 0.05% |
| `get_us` 分辨率 | 1 µs（2000 次采样 0 重复） | |
| `get_us` 单调性 | 20000 次 0 回退 | |
| 取一次时间戳 | **1.20 µs**（`get_count` 0.75 µs） | 这是每次测量的固定开销 |
| `delay_us(1/10/100/1000)` 误差 | 2 / 2 / 1 / 2 µs（1000 µs 时最大 48 µs） | |
| `osal_msleep(1)` | **19.996 ms** | 系统 tick 是 **20 ms**，不是 10 ms |
| `osal_udelay(1000)` | 983 µs | 忙等可用 |

**推论**：任何"每包 sleep 一下"的节奏控制都会变成 20 ms 粒度，所以主循环用忙等 `osal_udelay(500)`。

### 4.2 实验二：单板自环噪声底（role=loopback，204 秒、20400 包）

| p50 | p90 | p99 | p99.9 | max | 丢包 |
| --- | --- | --- | --- | --- | --- |
| **6 µs** | 7 µs | 8 µs | 11 µs | 125 µs | 0 |

这是**插桩自身的开销下界**（两次 `get_us` 2×1.2 µs + 组帧 + 同步回调），不含空口和协议栈。意义：**测量噪声比后面要测的 24 ms 小三个数量级**，所以双板数据不会是被仪器带偏的。

### 4.3 实验三：双板 SLE RTT（A=initiator，B=responder）

正式基线（40 Hz、40 B、3 ms 间隔、309 秒、12170 个有效样本）：

| p50 | p90 | p99 | p99.9 | max | mean | stdev | 速率 | 丢包 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **23.908 ms** | 24.656 | 27.048 | 33.606 | 41.638 | 23.826 | 1.016 ms | **40.0/s** | **0** |

三段采样（每段约 100 s）：p50 = 23.907 / 23.909 / 23.907 ms（差 2 µs），p99 = 27.61 / 26.95 / 26.95 ms。**可复现性成立。**

RSSI 实测 **−39 dBm**（近距离），对端处理耗时 `t3-t2` = 11 µs 均值 / 206 µs 最大。

### 4.4 实验四：连接间隔扫描（关键发现）

改 `sle_update_connect_param` 的间隔，每档跑 20 s：

| 连接间隔 | 写确认均值 | RTT p50 | RTT p90 | 速率 |
| --- | --- | --- | --- | --- |
| 12.5 ms | 65–67 ms | 99.96 ms | 112–125 ms | 9.6/s |
| 8 ms | 42.1 ms | 63.95 ms | 71.9 ms | 15.2/s |
| 6 ms | 31.8 ms | 47.95 ms | 53.9 ms | 20.4/s |
| 3 ms | 16.4 ms | **23.95 ms** | 24.1 ms | **40–41/s** |
| 0.75 ms（请求成功但未生效） | 18–19 ms | 23.97 ms | 47.7 ms | 36–37/s |

**结论：`RTT ≈ 8 × 连接间隔`，且有 24 ms 的地板。** 6 ms / 8 ms / 12.5 ms 三档是精确的 8.0 倍。实际生效的最小间隔是 3 ms（请求 0.75 ms 时协议栈回执说改成了，但空口没有更快）。

**8 倍怎么解释**：停止等模式下，理想是"2 个事件"（请求占一个事件，响应占下一个）。多出来的 6 个事件在协议栈内部——写请求要排队、要等对端回写响应、响应再从对端回来。写确认（cfm）均值约等于整个 RTT 的 2/3，说明**慢在"请求挤上去"，回程的 notify 只占小头**。

### 4.5 实验五：多包在途（流水线）——被证伪

假设"8 倍是停止等造成的，多发几个在途就能摊薄"。改窗口 = 8 重测：

- RTT p50 从 24 ms 涨到 **168 ms**；
- 吞吐仍是 **50 包/秒**左右（个别时段掉到 20/s）；
- 超时和重复各 430。

**结论：不行。** 链路可持续速率就是 41–50 对/秒，8 个事件的排队发生在协议栈/空口，不在我们的引擎。

## 5. 核心结论

### 5.1 这台芯片 + 这套 SDK 的数字

| 结论 | 数字 | 可信度 |
| --- | --- | --- |
| 双向 RTT 地板 | 24 ms | 高（三档间隔精确 8 倍，三段采样一致） |
| 实际最小连接间隔 | 3 ms | 高（0.75 ms 请求被接受但无效果） |
| 可持续请求-响应速率 | ≈ 41 包/秒 | 高（6 次独立测量 36–41/s） |
| 100 Hz 双向 RTT | **做不到** | 高 |
| 对端处理耗时 | 11 µs 均值 | 高（同板时钟） |
| 单向时延 | **不可测** | 高（时钟不同步） |

### 5.2 什么情况下这些数字会变

- **换传输层（BLE）**：BLE 连接间隔下限 7.5 ms（SLE 是 0.75 ms），理论 RTT 地板更高、速率上限约 66 包/秒。这就是 BLE 对照要验证的。
- **换芯片/换 SDK**：24 ms 和 41 包/秒都是"请求-响应路径 × 停等引擎"合出来的，不是星闪协议上限。换到 2 个事件往返的实现，3 ms 间隔下就是约 166 包/秒。
- **换环境**：目前只有一对板、一个房间、近距离（−39 dBm）。远距离、干扰、多设备并存都没测。

### 5.3 适用范围（重要，别被"通用示波器"误导）

星闪**没有**类似 ICMP ping 的通用协议。我们的 REQ/RSP 是本项目自定义的服务，只有烧了我们固件的设备才会回应。所以：

| 对象 | 能不能测 | 代价 |
| --- | --- | --- |
| 另外一块 Hi3863 / WS63 | ✅ 直接测 | 烧同一份固件 |
| 其它星闪芯片（Hi2821、BS21/BS25） | ⏳ 可移植 | 每个平台重写 300–500 行传输层 + 重新标定时基 |
| 商用星闪设备（鼠标、耳机、手机） | ❌ 只能被动监测 | 听广播、测活跃度与 RSSI 起伏，**测不了 RTT** |

## 6. 已知弱点与不确定性（诚实的清单）

评审时请重点怀疑这些：

### 6.1 "8 倍"的归因可能不完整

我们观察到"8 个事件"，但**没有证明**这 6 个额外事件具体花在哪。可能是：SSAP 写请求的排队、对端写响应的往返、协议栈任务的调度延迟、连接事件里的收发窗口划分。**没做过**的实验：在收包回调里立刻发下一包（而不是回主循环）、用 SDK 的 low-latency 通道、把探针任务优先级再提高。

如果 8 倍其实是"我们的用法"造成的（比如用了带响应的写请求），那 100 Hz 的判死就下早了。**这是最该被质疑的一条。**

### 6.2 单向时延为什么测不了

两块板的晶振各自漂，两个时钟之间有一个未知常数 δ。`t2-t1` 里混着 δ，无法分离。理论上可用"同一块板发两路、一路走线一路走空口"或"外部参考时钟"来做，成本远超本项目。所以**只报 RTT 和同板可测的分量**，这是设计选择，不是遗漏。

### 6.3 样本量

一对板、一个房间、一个固件版本，每组 3 次。**没有做过**：多对板、不同距离、有人走动/微波炉干扰、连续跑几小时看温漂。

### 6.4 BLE 对照未完成

BLE 两个文件（`link_ble_initiator.c` / `link_ble_responder.c`）刚写完，**只过了编译检查，没上过板**。不确定项：
- 预编译的 `libbt_host.a` 里是否包含 BLE GAP/GATT 的符号（SLE 是确定有的）；
- CCCD 是否需要在客户端显式写 0x0001 才能收到 notify（我们写了，但没验证）；
- BLE 广播/扫描的名字匹配是否能在两块板间稳定命中。

### 6.5 交付形态缺口

- **没有波形界面**。现在只有串口文本，用 `tools/analyze_log.py` 出统计表。方案里把 PC 工具排在 W2，尚未开始。
- **没有一键脚本**。同步、编译、烧录、采集、归档五步里有三步要人工点。
- **环境脆弱**：虚拟机 + RaiDrive 的 SFTP 映射今天断了两次，每次要人工重连。

### 6.6 结论的外推风险

"24 ms 地板"和"41 包/秒"极易被读者当成星闪的固有属性。实际上它们强烈依赖这套 SDK 的实现。我们已经在文档里要求所有数字带**平台签名**（chip / sdk / tick / min_interval / events_per_rtt / max_pps / noise_floor），但这一点容易被忽略。

## 8. 请重点回答的问题

按重要性排序，能答几条答几条：

1. **测量内核是否成立？** RTT = max(8×间隔, 24 ms)、41 包/秒上限、100 Hz 不可行——这三条结论的证据链有没有逻辑漏洞？如果只能再做一个实验来证伪"8 倍是 SDK 用法问题"，你会设计哪个实验？

2. **"无线示波器"这个产品定位成立吗？** 现在它是"两块专用板之间的 RTT 测量仪"。要变成对开发者真正有用的东西，缺的是波形界面，还是"能测第三方设备"，还是"能给出可行动的诊断结论"？三者优先级你怎么排？

3. **单向时延真的不能测吗？** 有没有成本可接受的办法（外部参考、同一时钟域打点、空中嗅探时间戳）能给出单向时延或它的上界？

4. **数据可信度够不够？** 一对板、一个房间、三段采样 p50 差 2 µs，这个可复现性足以支撑对外发布吗？还需要哪些最小验证（多板、长时间、温度）？

5. **最大风险是什么？** 在"6 周做出能演示的东西"这个约束下，哪个环节最可能崩：BLE 对照、PC 工具、被动监测、还是环境（虚拟机/SFTP）稳定性？

6. **该不该继续投入 BLE 对照？** 它会给结论带来什么增量？如果 BLE 也撞到 7.5 ms 地板，这个对照的价值是"证明星闪比 BLE 快"还是"证明测量方法通用"？

7. **如果目标改成"给星闪开发者一个可信的时延标尺"，现在这套东西离可用还差什么？** 请具体到"缺哪个功能、缺哪份文档、缺哪组数据"。

## 10. 一句话总结给评审

> 仪器是准的（噪声 6 µs 对信号 24 ms），数据是可复现的（三段 p50 差 2 µs），但**"能测一切星闪设备"是伪需求**——星闪没有通用 ping，测 RTT 必须两端都跑我们的固件。真正可交付的价值是：**一套可信的、带平台签名的时延标尺**，以及"换配置前后到底差多少"的对比能力。请重点质疑 §6.1（8 倍归因）和 §8 的第 2 问（产品定位）。
