# 星闪链路体检仪（NearLink LinkScope）· 项目方案

> 一句话：给星闪开发者做一台"无线示波器"，把"这条链路到底稳不稳"从感觉变成可复现的数字。
>
> 硬件基线：2 × BearPi-Pico H3863（Wi-Fi6 + BLE + SLE 三合一，已有）
> 周期：6 周（每周 6–10 小时）｜ 现金成本：≈ 0–60 元

---

## 1. 目标与非目标

### 要做
1. 端到端 **RTT 时延分布**（P50 / P90 / P99 / P99.9 / max）与**抖动**
2. **丢包 / 乱序 / 重复**检测（序号 + 超时判定）
3. 干扰条件下的**抗干扰保持率**（核心指标，见 §5.2）
4. **同板 BLE 对照**：同一颗芯片、同一根天线、同一个探针，切到 BLE 再跑一遍（这是本项目最硬的差异化）
5. PC 端实时可视化 + 一键跑实验矩阵 + CSV 落盘 + 自动出图

### 不做（明确砍掉，避免发散）
- ❌ 不做单向时延的绝对测量（需要跨板时钟同步，成本远超收益 → 用 RTT，见 §2.1）
- ❌ 不做协议栈抓包/解码（已有商用 SLE200 分析仪和竞赛作品，且工作量大）
- ❌ 不做 Mesh（单跳点对点已经足够支撑"链路质量"命题）
- ❌ 不做手机 App（前 6 周用 USB 串口，PC 端够用）

---

## 2. 三个关键设计决策

### 2.1 用 RTT，不做单向时延

单向时延需要 A、B 两块板共享同一时间基准。两块独立板子的晶振偏差异步，误差可达 ppm 级 → 在毫秒量级的时延上完全淹没信号。

**RTT 只需发起端自己的时钟**：A 记录 `t1` 发出，B 原样回显，A 记录 `t4` 收到，`RTT = t4 - t1`。全程单一时钟，无同步问题。

代价：RTT 含上下行两段 + B 的处理时间，不是"单程时延"。但对**对比实验**（有干扰 vs 无干扰、SLE vs BLE、包长 8B vs 250B）完全等价，且更保守。

**额外收益**：把 RTT 拆成三段，能定位瓶颈在哪：

```
RTT = (t2-t1) 上行传输   ← 只能半程估计（含未知时钟偏差 δ）
    + (t3-t2) B 处理时延 ← 同一时钟，精确可得
    + (t4-t3) 下行+AV处理 ← 同一时钟，精确可得
```

`(t4-t3)` 尤其重要：它包含 A 端从收到数据到打完时间戳的**自身调度抖动**。这个数如果很大，说明测量工具污染了被测对象（见 §2.3）。

### 2.2 同板 BLE 对照 —— 本项目的杀手锏

绝大多数星闪性能对比是"星闪板 vs 蓝牙耳机"，跨芯片、跨天线、跨固件，不可比。

H3863 一颗芯片同时有 SLE 和 BLE，**共用同一套射频前端和 PCB 天线**。把探针协议原样跑在 BLE 上，就得到一个变量唯一的对照：

| 变量 | SLE 组 | BLE 组 |
|---|---|---|
| 芯片 | Hi3863 | Hi3863（同一颗） |
| 天线 | 板载 PCB | 同一根 |
| 固件框架 | 本项目 | 本项目（仅换传输层） |
| 探针协议 | 8B 帧 + 序号 | 完全相同 |
| 供电/位置/温漂 | 相同 | 相同 |

这是评委会认的"控制变量"。设计上要求：**传输层抽象成一层 `link_ops` 接口**（`send()` / `on_recv()` / `now_us()`），SLE 和 BLE 各实现一份，上层统计代码零改动。

### 2.3 先测"仪器噪声底"，再测链路

这是最容易被忽略、也最容易被答辩问倒的一点：**你的测量工具自身抖动必须远小于你要测量的差异。**

做法（W1 必做）：
1. **本地回环**：同一块板上把探针帧从内存发出→回调收回，不走空口，测 `t4-t1` 的分布 → 得到"纯软件路径抖动"
2. 若本地回环的 P99 已经接近你想要的空口时延差异（比如 1–2 ms），则：
   - 抬高探针任务优先级、关掉 `osal_printk` 日志、时间戳放在回调第一行
   - 必要时把打点放进中断/高优先级上下文
3. 报告中**明确写出噪声底**，例如："本工具噪声底 P99 = 0.21 ms，故仅对 > 0.5 ms 的差异作结论"

有了这句话，你的数据才可信。

## 3. 探针协议（帧格式）

单帧必须小（默认 40B 上限，性能模式下 250B），且**不能有变长编码**（解析开销会污染时间戳）。

### 3.1 REQ（A → B，发起端→响应端）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `magic` | 0xA5，快速丢弃杂包 |
| 1 | 1 | `type` | 0x01 = REQ |
| 2 | 2 | `seq` | u16 自增，回绕；用于丢包/乱序/重复 |
| 4 | 4 | `t1_us` | A 端发出时刻，u32 微秒 |
| 8 | 4 | `cfg_id` | 当前实验配置编号，便于事后归因 |
| 12 | n | `fill` | 填充字节，用于把包长拉到 8/64/250B 档位 |

### 3.2 RSP（B → A，原样回显 + 打点）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `magic` | 0xA5 |
| 1 | 1 | `type` | 0x02 = RSP |
| 2 | 2 | `seq` | 原样回显 |
| 4 | 4 | `t1_us` | 原样回显 |
| 8 | 4 | `t2_us` | B 收到 REQ 的时刻 |
| 12 | 4 | `t3_us` | B 发出 RSP 的时刻 |
| 16 | 4 | `cfg_id` | 原样回显 |

RSP 固定 20B。`(t3-t2)` = B 侧处理时延，同一时钟内有效。

### 3.3 关键实现约束
- **B 侧处理必须极简**：收到 REQ 后只做「读时间戳 → 填 RSP → 立即回发」，不做日志、不做 UART 转发、不做条件判断以外的任何事。
- **时间戳在回调第一行取**，早于任何 `memcpy` / 分支 / 打日志。
- **单包上限**：默认 `SLE_UART_SERVER_SEND_BUFF_MAX_LEN = 40`；`CONFIG_SAMPLE_SUPPORT_PERFORMANCE_TYPE` 下为 250。→ 250B 档实验必须在性能模式下跑，这本身就是一个实验结论（"大包必须开性能模式"）。
- **u32 微秒回绕**：约 71.6 分钟回绕一次。统计时用 `(uint32_t)(t4 - t1)` 的无符号减法，天然正确；但跨回绕的长实验要留意。

## 4. 固件结构

### 4.1 分层

```
┌─────────────────────────────────────────────┐
│  app: 探针调度器 (发送节奏 / 超时 / 配置命令)  │
├─────────────────────────────────────────────┤
│  stats: 直方图 · 分位数 · 丢包 · 乱序 · 抖动   │  ← 与传输层无关
├─────────────────────────────────────────────┤
│  probe: 帧编解码 (REQ/RSP)                   │
├─────────────────────────────────────────────┤
│  link_ops:  send / on_recv / now_us          │  ← 抽象层，关键
├──────────────┬──────────────┬───────────────┤
│ sle_impl     │ ble_impl     │ loopback_impl │
│ (ssapc/ssaps)│ (GATT)       │ (噪声底校准)   │
└──────────────┴──────────────┴───────────────┘
```

**为什么要有 `loopback_impl`**：它让"噪声底测量"成为同一套代码的一个配置项，而不是另写一个临时程序。

### 4.2 角色与镜像

两块板烧**同一份固件**，角色由串口命令 / GPIO 电平 / 按键在启动时决定：

- `role=initiator`（A）：按设定速率发 REQ，收 RSP，算 RTT，做统计
- `role=responder`（B）：收 REQ，立即回 RSP
- `role=loopback`（自测）：不发空口，只跑本地路径

好处：一块板烧坏了/刷错版本，另一块直接改角色顶上；也方便做 A、B 互换的公平性检查（"是不是某一端的调度更差"）。

### 4.3 目录建议

```
linkscope/
├── application/
│   └── linkscope/
│       ├── linkscope_main.c        # 入口 + 角色分派 + 串口命令
│       ├── probe.c / probe.h       # 帧编解码
│       ├── stats.c / stats.h       # 直方图、分位、丢包
│       ├── link_ops.h              # 传输层抽象
│       ├── link_sle.c              # 基于 sle_uart_client/server 改写
│       ├── link_ble.c              # 基于 ble_uart 改写
│       └── link_loopback.c
├── tools/
│   ├── linkscope.py                # pyserial 采集 + 实时曲线
│   ├── run_matrix.py               # 一键跑实验矩阵
│   └── analysis.py                 # CSV → 图表 / 评分
└── docs/
    ├── protocol.md
    └── results/
```

**起点代码**：直接以 `application/samples/products/sle_uart/` 为骨架改（server 端 `ssaps_server_write_request_cbk` 就是你放"立即回发"的地方，client 端 `ssapc_write_req` + `sle_uart_notification_cb` 是 A 端收发路径）。

## 5. 指标与评分

### 5.1 原始指标（A 端本地计算）

| 指标 | 定义 |
|---|---|
| 丢包率 | `1 - 收到RSP数 / 发出REQ数`（超时阈值可配，默认 50 ms） |
| 乱序 | `seq` 小于已见最大值的次数 |
| 重复 | 同一 `seq` 出现多次 |
| P50 / P90 / P99 / P99.9 | RTT 分位数（对数分桶直方图，见下） |
| 抖动 | 相邻样本 RTT 差分的平均绝对偏差（类 RFC3550） |
| 吞吐上限 | 背靠背写、加大在途包数，直到丢包率 > 1% |

**内存约束**：H3863 SRAM 小，不能缓存全部样本。用**对数分桶直方图**：

```
桶边界 = 1us, 1.25us, 1.56us, ... 每倍频程 8 桶，到 200ms
桶数 ≈ 8 × log2(200000) ≈ 8 × 17.6 ≈ 141 桶
每桶 u16 计数 → 282B，完全放得下
```

分位数从桶内插值算。**同时保留抽样原始样本**（1/20 抽样）用于画真实散布图和事后复核。

### 5.2 抗干扰保持率（核心指标）

```
保持率 = 干扰条件下的评分 / 无干扰时的评分
```

这才是星闪"抗干扰、跳频"卖点的量化表达。BLE 对照组的保持率往往显著更低——这个对比就是本项目的核心结论。

### 5.3 综合评分（0–100）

```
Score = 100 × (0.40·f_lat + 0.25·f_jit + 0.25·f_loss + 0.10·f_thr)

f_lat  = clamp(1 - (P99 - P99_base) / (10·P99_base), 0, 1)   # P99 恶化 10 倍则归零
f_jit  = clamp(1 - jitter_ms / 20, 0, 1)
f_loss = 1 - loss_rate
f_thr  = clamp(thr_mbps / thr_max_mbps, 0, 1)
```

`P99_base` = 同配置、无干扰条件下的 P99（即"该配置的理论基线"）。这样评分是**相对自身基线**的退化程度，避免不同配置间的绝对数值不可比。

评分只用于演示和汇报，主结论仍用原始指标（评委更认原始数据）。

## 6. 六周里程碑

| 周 | 目标 | 交付物（可验收） |
|---|---|---|
| **W1** | 环境跑通 + SDK 能力确认 + 噪声底 | 双板打印 `seq,t1,t4,rtt`；《平台能力确认表》；噪声底数值 |
| **W2** | 探针协议闭环 + 计时精度标定 | 100Hz 稳定跑 10 分钟无崩溃；计时精度实测报告 |
| **W3** | 统计引擎 + 串口配置命令 | 板端直接输出 P50/P99/丢包/乱序；配置可改 |
| **W4** | PC 工具 | 实时曲线 + CSV + 一条命令跑完一组实验 |
| **W5** | 干扰矩阵 + BLE 对照 | 完整数据集（≥ 60 组配置，每组 3 次重复） |
| **W6** | 评分模型 + 报告 + 开源整理 | 图表、结论、README、可复现脚本 |

**W1 是最关键的一周**，因为它同时验证"能不能做"和"测得准不准"。如果 W1 的噪声底过大或 SDK 缺关键接口，要在 W1 结束时决定降级方案（见 §8），而不是拖到 W5。

### 6.1 里程碑调整（2026-11-06，W1 实测后）

依据见 `docs/W1-平台能力确认.md` §5 与 `docs/项目日志.md` P26：

- **100 Hz 在这套 SDK 上做不到**：实测 `RTT = max(8 × 间隔, 24 ms)`，吞吐上限 ≈ 41 包/秒，加在途窗口也不放大（8 窗口仍是 50 包/秒、p50 反涨到 168 ms）。W2 验收从"100 Hz 跑 10 分钟"改为"**40 Hz（固定 3 ms 间隔）跑 3 分钟 × 3 次，0 超时 0 重传**"；100 Hz 降级为可选探索（low-latency 数据通道 / 无连接广播），不阻塞主线。
- **硬件只有 2× BearPi-Pico H3863**：把 PC 工具（原 W4）提前到 **W2**，因为"看到波形"是项目叙事的核心；**W3 增加被动监测模式**（唯一不需要对端配合的工作模式，见 §11.3），用它兑现"能看任意星闪设备"。
- W5 干扰矩阵按实际可测维度重算（包长 × 速率 × 间隔 × 干扰源 × 距离），不再按"≥60 组"硬凑。

## 7. 实验矩阵

固定：距离、朝向、供电方式必须**每次记录并保持一致**（这是可重复性的前提）。

| 因素 | 档位 | 说明 |
|---|---|---|
| 干扰源 | 无 / WiFi 满载下载 / 手机热点 + iperf / BLE 广播风暴 | 用手机或笔记本，脚本化启停 |
| 距离 | 0.5 m / 2 m / 5 m / 10 m / 隔一堵墙 | 卷尺量，支架固定 |
| 包长 | 8 B / 64 B / 250 B | 250B 需性能模式 |
| 探针速率 | 10 / 50 / 200 Hz | 200Hz 可能受连接间隔限制 |
| 链路模式 | 默认 / low-latency / performance(MCS) | `sle_low_latency_tx_register_callbacks`、`sle_uart_server_sample_set_mcs` |
| 连接间隔 | 10 ms / 30 ms / 50 ms | 若 SDK 可配 |
| 传输层 | SLE / BLE | 同板对照 |

**规模控制**：全组合 4×5×3×3×3×3×2 太多。用**单因素扫描 + 少量交叉**：
- 基线组（无干扰、2m、64B、50Hz、默认、SLE）跑全部干扰档
- 每个因素单独扫一遍（其余固定在基线）
- 只对"距离 × 干扰"做二维交叉（这是最可能有交互效应的）
- 总计约 60–70 组，每组 60 s + 3 次重复

## 8. 风险与降级方案

| # | 风险 | 概率 | 影响 | 降级方案 |
|---|---|---|---|---|
| R1 | 缺微秒级单调时基 | 中 | 高 | 用硬件定时器 / 系统 tick，实测分辨率后改用 RTT 的整数 tick 计数；报告注明分辨率 |
| R2 | 自身调度抖动 > 被测差异 | 中 | 高 | 提优先级、去日志、时间戳前置到回调首行；报告噪声底，只对超噪声底差异下结论 |
| R3 | SDK 不暴露 RSSI / 重传计数 | 高 | 中 | 用 RTT 抖动 + 丢包率作代理指标；RSSI 若能从连接信息取到就加分，取不到不阻塞主线 |
| R4 | 探针速率被连接间隔卡死 | 高 | 中 | 开 low-latency/turbo；或加一路"无连接广播单向测量"作为高频补充（只测相对变化） |
| R5 | 单包 250B 上限太小，打不满吞吐 | 高 | 低 | 吞吐实验改为背靠背连续写 + 加大在途包数（类似 AIMD 加压），测"可持续吞吐"而非"单包速率" |
| R6 | 干扰不可重复，数据散 | 高 | 中 | 固定距离/朝向/支架；干扰脚本固定；每档 3 次取中位数；报告给出方差 |
| R7 | UART 115200 成瓶颈，原始样本传不完 | 中 | 低 | 只传聚合结果 + 1/20 抽样；或提到 921600（例程里 `SLE_UART_BAUDRATE = 115200`，需改） |
| R8 | 只有 2 块板，做不了三节点 | 低 | 低 | 干扰源用外部设备；对照实验靠同板 BLE（§2.2），本来就不需要第三块板 |
| R9 | 板载无 USB 转串口，需外接模块 | 中 | 低 | 备 2 个 CH340/CP2102；W1 第一天确认 |

### W1 SDK 能力确认表（逐项打勾）

从官方 `sle_uart.c` 已确认存在、需要你实测语义的接口：

- [ ] `sle_low_latency.h` → `sle_low_latency_tx_register_callbacks()`：`low_latency_tx_cb` 是否为零拷贝直发路径？回调上下文是什么？返回 `NULL` 与返回数据帧的差异？
- [ ] `sle_uart_server_sample_set_mcs(conn_id)`：MCS 有哪些档位？在什么条件下生效？切换后 RTT 变化多少？
- [ ] `CONFIG_SAMPLE_SUPPORT_PERFORMANCE_TYPE`：确认单包上限 250B；`SLE_UART_SERVER_MSG_QUEUE_LEN = 5` 是否成为瓶颈
- [ ] `ssapc_write_req()`：连续调用的流控行为？是否有在途包数上限？失败返回什么？
- [ ] `sle_connection_manager`：连接间隔能否通过 API 改？最小值是否 10 ms？
- [ ] 微秒时基：`uapi_tcxo_get_us()` 是否存在（WS63/Hi3863 系列常见）？单调性？回绕周期？
- [ ] RSSI：`ssapc` 连接信息或 `sle_connection_manager` 里是否有 rssi 字段？
- [ ] 实测任务优先级 28（`SLE_UART_TASK_PRIO`）下的调度抖动

**做法**：写一个最小 `hello_timing` 程序，只做三件事——取时间戳、翻转 GPIO、打印差值。用示波器或逻辑分析仪看 GPIO 翻转间隔 vs 打印差值，就知道时基和调度的真实水平。没有示波器就用"已知延时 + 统计方差"间接判断。

## 10. 演示与叙事（答辩/开源 README 用）

**开场一句话**："星闪的宣传是 20μs 级时延和抗干扰，但社区里没人能拿出可复现的测量工具——所有人都在凭感觉。我们做了这个。"

**三段式演示**：
1. **静默基线**：PC 屏幕上 RTT 曲线平稳，P99 = x ms，评分 95
2. **拉起干扰**：旁边手机开始满载下载 → 曲线抖动，P99 涨到 y ms，评分掉到 60
3. **切 BLE 对照**：同一块板、同一个探针，同样干扰下 BLE 掉到 z ms，评分 25 → **保持率对比**

**核心结论句式**（用你自己的数据填）：
> 在 WiFi 满载干扰下，SLE 的 P99 时延从 a ms 退化到 b ms（保持率 c%），同期同板 BLE 从 d ms 退化到 e ms（保持率 f%）。星闪的抗干扰优势在 [某档距离/包长] 下最显著，在 [某档] 下消失。

**开源价值**：这个工具本身会被别人用来测他们自己的星闪产品——比"又一个应用 demo"的生命周期长得多。README 里放"如何用 LinkScope 测你自己的模组"，这是社区会 star 的东西。

## 11. 落地形态、可测设备与适用边界

### 11.1 形态：两个探头 + 一个显示器

```
    ┌──────────┐        SLE 空口            ┌──────────┐
    │ 探头 A   │ ◄────  REQ / RSP  ────►   │ 探头 B   │
    │ (发起端) │   40B, 固定 3ms 间隔        │ (响应端) │
    └────┬─────┘                            └────┬─────┘
         │ USB 串口（数据）                       │ USB（供电 + 日志）
    ┌────┴────────────────────────────────────────┴─────┐
    │          PC 上位机 NearLink Scope                  │
    │  实时波形 · 直方图 · 分位数 · 丢包 · 一键出报告      │
    └───────────────────────────────────────────────────┘
```

**铁律：PC 只显示和配置，不参与计时。** 时间戳全部在板端取（实测 40 ticks/µs、1 µs 分辨率、单次开销 1.20 µs）；若让 PC 计时，USB 串口毫秒级迟滞会把待测量淹掉。这是"仪器"与"脚本"的分界线。

交付四件套：**两块探头板 + PC 程序 `tools/nlscope.py` + 可复现实验脚本 + 带平台签名的报告模板**。

### 11.2 一次测试的流程

| 步 | 动作 | 耗时 |
|---|---|---|
| 1 | 两块探头插 USB 供电，按固定距离/角度/遮挡摆好 | 1 分钟 |
| 2 | 打开上位机，选串口，选配置（包长/速率/间隔/角色） | 10 秒 |
| 3 | 点"开始"：A 扫描 → 连接 → 配对 → 发现属性 → 链路就绪 | 约 3 秒 |
| 4 | 跑设定时长，实时出波形；每组配置重复 3 次 | 3 分钟 × 3 |
| 5 | 点"出报告"：CSV + 分位数表 + 波形图 + 评分 | 10 秒 |

干扰变量（旁边开 WiFi/蓝牙下载、金属板遮挡、人手遮挡）是在这套流程外面套的一层，即 §7 的实验矩阵。

### 11.3 三种工作模式

| 模式 | 怎么连 | 能测什么 | 可测对象 |
|---|---|---|---|
| **链路模式**（主力） | A ↔ B 两块探头 | RTT 分布、丢包、抖动、三段分解、BLE 同板对照 | 两块 H3863 探头；任何烧了 responder 的星闪板 |
| **设备模式** | A 探头 ↔ 被测设备 | 同上，被测方换成客户产品 | 星闪开发板/模组（需 responder port）；**固件不可改的产品不行** |
| **监测模式**（被动） | 单探头，只听不连 | 活跃度、广播间隔、RSSI 起伏、连接事件节奏 | **任意在广播的星闪设备**（含手机/耳机/鼠标），但**测不了 RTT** |

### 11.4 可测设备清单（老实版）

| 设备 | 能否测 | 前提 |
|---|---|---|
| 2× BearPi-Pico H3863（现有） | ✅ 现在就能 | 无 |
| 其他 WS63/Hi3863 开发板 | ✅ 小改 | 引脚/UART 配置重编 |
| Hi2821 / BS21 / BS25 等星闪芯片 | ⏳ 需移植 | 每芯片 300–500 行 `link_ops` + 重标定时基与噪声底 |
| 客户自己的星闪产品 | ⏳ 需配合 | 产品固件可塞 responder |
| 商用第三方设备（手机/耳机/鼠标） | ⚠️ 仅监测模式 | 它们不会回我们的帧，测不了 RTT |
| 手机当 A 端 | ⚠️ 勉强 | 需 app + 系统开放 SLE 服务端；OS 调度会吃掉 µs 级精度 |

### 11.5 平台签名：跨 SDK 可比的前提

任何一组数字必须带这张表，否则不得跨平台比较（填不出来就不下结论）：

```ini
chip        = ws63 / hi3863
sdk         = bearpi-pico_h3863-master @ <commit>
tick_us     = 40          # 实测值，头文件宏写的是 24
min_interval= 3ms         # 实测生效下限（再低不生效）
events_rtt  = 8           # rtt / 生效间隔，反映协议栈排队深度
max_pps     = 41.7        # 1 / (8 × 3ms)
noise_floor = 6µs (P50) / 8µs (P99)   # loopback 实测
sched_tick  = 20ms        # osal_msleep(1) 实际 19.996ms
```

`events_rtt` 是最有信息量的一个数：它直接说明"这家的协议栈是发一次就上空中，还是要排队几个连接事件"。

### 11.6 不做（适用边界）

1. **不测单向时延**——两板晶振不同步，δ 未知，只报 RTT 及其分解（见 §2.1）。
2. **不测第三方设备的 RTT**——RTT 必须对端回帧；商用产品不会配合。
3. **不宣称"星闪整体性能"**——只给"这套 SDK + 这组配置 + 这个环境"下的结论，结论随 §11.5 的签名走。
4. **不用 PC 侧时间戳**——见 §11.1。
5. **不对小于噪声底的差异下结论**——loopback 底噪 6 µs 是报告的下限。

### 11.7 通用化的三档路线

| 档 | 形态 | 对端要求 | 通用性 | 成本 |
|---|---|---|---|---|
| **A** | 两块 H3863 探头 | 都烧本固件 | 只测自家探头 | 已完成 |
| **B** | 可移植 responder | 任意星闪开发板/模组装一份小固件 | 芯片可换 | 每芯片 300–500 行适配 + 标定 |
| **C** | 被动监测 | 不需要 | 任意星闪设备（含商用产品） | 约 1 周（复用现有 `timing` 底座） |

A 给"值"（精确 RTT），C 给"面"（任意设备可见），B 是"值 × 面"的交集。三者合起来，才配叫"星闪无线示波器"。
