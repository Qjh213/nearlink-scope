## 一、环境与工具链

### P01 · DSH 沙箱写工作区失败

**现象**：往 `E:\nearlink-scope` 写任何文件都报
`SetNamedSecurityInfoW failed: 拒绝访问 (Win32 5)`。读没问题，写全失败。

**定位**：这不是 DSH 的 bug，是目录 ACL 本身坏了——DSH 每次写文件前会重设属主/权限，
这一步被系统拒绝。用内置技能 `diagnose-windows-sandbox-acl` 跑一遍，它把每一级祖先进去查，
结论：该目录的 ACL 缺 `WRITE_OWNER`，且继承链中断。

**解决**：按技能产出的回滚脚本修 ACL，修复后校验 `grants verified`。
后来又出现一次（见 P02），第二次修完才彻底通。

**教训**：Windows 上"MCP/沙箱工具说写不了"先别急着换工具，八成是 ACL，不是权限模型。

### P02 · 子目录仍被拒 + Low 完整性标签

**现象**：P01 修完根目录可写了，`firmware/` 仍然被拒。

**定位**：`firmware` 单独缺 `WRITE_OWNER`；另外根目录被打了 **Low 完整性标签**——
结果是**旧子目录对沙箱只读，新建目录反而可写**。这个"新能写、旧不能写"的规律是判断依据。

**解决**：对 `firmware` 单独再跑一次同样的修复；后续把会话切到 `danger-full-access`，问题不再出现。
修复过程的 ACL 备份与回滚脚本留在 `E:\nearlink-scope-acl-recovery`（确认没问题后可删）。

### P03 · Windows 编不了

**现象**：宿主 Windows 上没有 cmake、ninja、gcc、clang。
SDK 自带一份 Windows 版 RISC-V 工具链（`tools/bin/compiler/riscv/.../win`），但**缺 DLL，起不来**。

**解决**：接受现实——**编译只在 Ubuntu 虚拟机里做**。Windows 端只做源码编辑、静态检查（zig）和烧录。

**教训**：不要试图在 Windows 上凑一套交叉编译环境，SDK 的构建脚本（`build.py` + cmake + bash）
本身就是 Linux 假设，硬凑的收益远小于成本。

### P04 · 虚拟机看不见 E 盘

**现象**：VM 的 `.vmx` 里**没有任何共享文件夹**配置，`/mnt/hgfs` 不存在，
VM 里根本访问不到宿主机的 `E:\nearlink-scope`。

**解决**：VM 的磁盘被 RaiDrive 以 SFTP 映射成 `Z:`（`\\RaiDrive-29301\SFTP`），
即"VM 根分区"在 Windows 上可见。于是形成单向链路：

```
E:\nearlink-scope  (唯一真源，可 git)
        │  firmware/scripts/sync-to-sdk.ps1
        ▼
Z:\home\bearpi\project\bearpi-pico_h3863-master  (VM 里的构建输入)
        │  python3 build.py -c ws63-liteos-app
        ▼
output/ws63/fwpkg/.../ws63-liteos-app_all.fwpkg  (产物，Windows 侧直接可见)
```

**规矩**：只改工作区，再同步；**永远不要在 VM 里直接改 linkscope 源码**（会被下次同步覆盖）。
不把项目放 Z: 的理由：VM 一关机 Z: 就没了，而且在 SFTP 上跑 git、编辑都慢。

### P05 · 两份 SDK 不一致

**现象**：`E:\Starklink\bearpi-pico_h3863-master` 和 `Z:\home\bearpi\project\bearpi-pico_h3863-master`
是同一份 SDK 的两个副本，但内容不同：E: 那份没有 `output/`，`sle_uart_server_adv.c` 还是
把本机地址写死成 `01:02:03:04:05:06` 的旧版本。

**解决**：以 **Z: 为准**。判据不是"哪份新"，而是：Z: 有 `output/` 和 `local_fw/` 历史固件、
`.bash_history` 里有构建命令、adv.c 已经是 `sle_get_local_addr()` 版本——**它是活动构建树**。

### P06 · zig 的 `-fsyntax-only` 不能用

**现象**：本机没有 C 编译器，装了 `ziglang`（pip 装到 `.tools/py`）当编译器用。
但 `python -m ziglang cc -fsyntax-only xxx.c` 在这台机器上抛 `FileNotFoundError`。

**解决**：不用 `-fsyntax-only`，改成 `-c -o E:\nearlink-scope\.tools\build\xxx.o` 正常出目标文件。
配合 **SDK 真头文件**（`-I` 指向 `include/`、`include/driver`、`kernel/osal/include` 各子目录等）
做语法+类型检查，效果比 `-fsyntax-only` 更好——能抓到头文件里的类型不匹配。

`.tools/` 已加进 `.gitignore`。

**追加（2026-11-06）：zig 还有两个环境坑**

1. `zig: error: unable to open global cache directory 'C:\Users\…\Temp\…': AccessDenied`
   —— 缓存默认落在系统 TEMP，本机的沙箱不让写。解决：`ZIG_GLOBAL_CACHE_DIR` / `ZIG_LOCAL_CACHE_DIR`
   显式指到 `.tools\build\<任务>\zig-cache`。
2. `zig: error: unable to make temporary file: Permission denied`
   —— 这个更隐蔽：编译本身能过，只在**链接**那一步炸，而且 PowerShell 里 `$LASTEXITCODE` 看着是 0，
   表现成"编译成功但产物不存在"。原因是 zig 最后写临时文件才读 `TMPDIR/TMP/TEMP`。
   解决：把 `TMPDIR`、`TMP`、`TEMP` 一起指到工作区（`.tools\build\host-test\tmp`）。

两个脚本（`firmware\scripts\check-sdk-syntax.ps1`、`firmware\linkscope\test\run_host_test.ps1`）都已改成这样。

## 二、对 SDK 的认识修正

### P07 · 方案文档里三个不存在的东西

| 方案原文 | 实际情况 |
|---|---|
| `sle_uart_server_sample_set_mcs(conn_id)` | 本 SDK **没有**这个函数，真名是 `sle_set_mcs(conn_id, mcs)` |
| `CONFIG_SAMPLE_SUPPORT_PERFORMANCE_TYPE` 下 250B | 本 SDK **没有**这个宏；单帧上限由 MTU（协商 520）和 server 的 256B 栈缓冲决定 |
| `uapi_tcxo_get_us` 是否可用 | 可用，返回 u64；但**计数频率不是文档里写的 24**（见 P11） |

**教训**：方案阶段的"API 清单"只能当线索。**凡是要写进代码的 API，必须去头文件核一遍签名**，
否则会在编译期返工（本 SDK 编译带 `-Werror`，一个错名就整包编不过）。

### P08 · low latency 是"拉模式"

**现象**：原本打算用 `sle_low_latency_tx_register_callbacks()` 做"每包触发一次"的发送打点。

**根因**：看 `sle_low_latency.h` 才发现它的模型是：协议栈按你注册的 rate
（125Hz / 250Hz / 500Hz / 1k / 2k / 4k / 8kHz）**主动回调要数据**，回调里返回 `NULL` 就不发。
是"协议栈拉"，不是"你推一包它打一次点"。

**解决**：不用它做逐包 RTT。改成自己在应用层做 **REQ/RSP 停等**（一包在途，回包才发下一包），
时间戳打在应用层回调里。low latency 路径留给 W3 的"高频上报"对比实验。

### P09 · `t4 - t3` 不是回程时延

**根因**：`t3` 由 B 打、`t4` 由 A 打，**两个时钟之间有一个未知偏差 δ**。
所以 `t4 - t3` 里混着 δ，绝对值没有意义（δ 可能远大于要测的时延）。

**解决**：`docs/protocol.md` 的时间分解改正为：
- `t3 - t2`（B 内，同一时钟）→ **精确**，对端处理时间
- `t4 - t1`（A 内，同一时钟）→ **精确**，RTT
- `t4 - t3`（跨时钟）→ 只能看趋势/抖动，不能报绝对值

### P10 · `osal_msleep(1)` 是 20ms

**现象**：想用 `osal_msleep(1)` 做 1ms 节拍，结果实测每次睡 **19996µs**（19.68–20.20ms）。

**根因**：LiteOS 的 tick 是 **20ms（50Hz）**，`msleep(1)` 向上取整到 1 个 tick。
方案文档原来写的是"tick 默认 100Hz，所以是 10ms"——也不对，实测就是 20ms。

**交叉验证**：连续 50 次 `osal_msleep(1)` 的串口墙钟是 **999.8ms**，对名义 1000ms，误差 <0.05%。
说明"20ms×50"是对的，不是打点算错了。

**解决**：所有需要 100Hz 以上节奏的地方一律**忙等**（`osal_udelay(500)`），
并承担"占满一个核"的代价（优先级 28，协议栈任务仍可抢占）——这直接引出 P15 的看门狗问题。

### P11 · 计数频率是 40，不是 24

**现象**：头文件宏 `TCXO_TICKS_PER_U_SECOND` 写的是 **24**，但用它换算的时间明显不对。

**实测**：真实频率是 **40 ticks/µs**（40MHz 晶振）。用 40 做除数，50×`msleep(1)` 墙钟对得上（见 P10）。

**配套实测**（`-Role timing`，数据见 `docs/W1-平台能力确认.md` §5.1）：

| 项 | 值 |
|---|---|
| `uapi_tcxo_get_us()` 分辨率 | 1µs（2000 次连续读 0 重复） |
| 单调性 | 20000 次读 0 回退 |
| 单次开销 | **1.20µs**（`get_count` 0.75µs） |
| 最小可分辨计数间隔 | 31 ticks ≈ 0.78µs |
| `delay_us(1/10/100/1000)` 误差 | 2 / 2 / 1 / 2 µs（1000µs 档最坏 48µs） |
| `osal_udelay(1000)` | 983µs |

**结论**：打两次点就吃掉 **2.4µs**，这和单板自环 6µs 的底噪是同一量级。
测 µs 级差异时要改用 `get_count`（事后换算），或者把打点开销当常数从 RTT 里减掉。

### P12 · 两板会撞地址

**现象**：E: 副本的 `sle_uart_server_adv.c` 把本机地址写死成 `01:02:03:04:05:06`。
两块板同时烧同一份固件 → 地址完全相同 → 扫描/连接行为不可预期。

**解决**：用 Z: 那份（`sle_get_local_addr()` + 全零回退）。

**遗留风险**：实测两块板启动时都打印 `init_sle_mac failed!!!`，
于是都走了"全零回退"分支，广播地址都是 `0xCA 0xCA 0xCA 0xCA 0xCA 0xCA`——**两板可能仍然同地址**。
目前 A 能连上 B 说明链路可用，但如果后面出现"连错板/连不上"，这是第一嫌疑。
备选方案：用编译期宏给 A/B 各写一个固定但不同的地址。

## 三、固件正确性（主机单测抓到的）

### P13 · `rtt == 0` 被判成坏样本

**现象**：主机单测里 loopback 的 RTT 恒为 0（同一进程里 `get_us` 前后没走完 1µs），
engine 的合法性判据写的是 `rtt > 0 && rtt < timeout`，于是**所有样本都被丢掉**。

**解决**：判据改成 `rtt >= 0 && rtt < timeout`。真机上 RTT 不可能为 0，但下界不该由业务逻辑臆断。

### P14 · 先 `send` 后置"在途"，loopback 回包被判 unsolicited

**现象**：loopback 链路是**同步**的——`link->send()` 在返回前就把 RSP 交给了 engine。
如果代码顺序是「send() → 置 pending」，回包时 pending 还是 0，被记成"没有在途请求的主动回包"。

**解决**：顺序改成「**先置 pending，再 send**」。这条对 SLE 同样正确：写请求是异步的，
回包一定晚于 `ssapc_write_req()` 返回，先置标志不会有副作用。

**教训**：这类"同步 vs 异步"的顺序 bug，只有用**同步的假链路**（loopback）跑集成测试才能稳定复现。
所以 `link_ops` 抽象 + loopback 实现是刚需，不是装饰。

## 四、看门狗与部署

### P15 · 每 18.4 秒必重启（最贵的一个坑）

**现象**：initiator 角色烧进 A 板后，串口每 **18.4 秒**出现一次：

```
APP|Oops:NMI
APP|Reboot core:2 cause 0x2008
```

连续 5 次，任务表 dump 显示应用任务还活着，但系统被复位。

**定位**：
1. `mcause = 0x8000000C` → 查 `exception_riscv.c`：`NMI_INTERRUPT = 0x8000000C`。
2. 同一个文件里，NMI 处理函数会调 `uapi_watchdog_kick()` 并打印任务信息——**这是看门狗咬的**。
3. `.config` 里 `CONFIG_WATCHDOG_ALREADY_START=1`，即看门狗由系统启动，但**没有人喂**。
4. 对照组：`timing` 角色用 `osal_msleep` 空转 93 秒不崩；`initiator` 是 500µs 忙等主循环。
   → **忙等占满 CPU，把低优先级的喂狗任务饿死了**。

**解决**：在主循环里自己喂狗，间隔 500ms：

```c
if ((uint32_t)(now_ms - last_kick_ms) >= LS_WDT_KICK_MS) {
    (void)uapi_watchdog_kick();
    last_kick_ms = now_ms;
}
```

喂狗点放在「`ls_engine_tick()` + `report_drain()` 都正常走完」之后：
真卡死时就不再喂，看门狗仍然能兜底——**不要把喂狗放在循环开头**，否则卡死也会被喂活。

**验证**：
- B 板 loopback 连续 **20400 包 / 204 秒**无重启，且 `seq` 严格连续（间隔恒为 1，重启会把 seq 归 1）
- A 板 initiator 重烧后跑 **108 秒无重启**（重烧前是 18.4 秒必挂）

### P16 · `[string]` 参数把 `$null` 变成空串

**现象**：`sync-to-sdk.ps1` 写出的 `.config` 里出现 `CONFIG_LINK_SCOPE_PAYLOAD_BYTES=`（空值）。

**根因**：PowerShell 的 `[string]` 类型参数会把 `$null` 强制转成 `""`，
函数里判断 `$null -eq $x` 永远为假。

**解决**：改用 `[string]::IsNullOrEmpty($x)` 判断，并且**未显式传参时不要覆盖已有值**。

### P17 · RaiDrive 映射盘上 `Copy-Item` 报"无法用自身覆盖项"

**现象**：往 Z:（SFTP 映射）覆盖文件时，`Copy-Item -Force` 抛
`无法用自身覆盖项`。

**解决**：绕开 PowerShell 的 Copy-Item，用 .NET：
`[System.IO.File]::Copy($src, $dst, $true)`。

### P18 · `# CONFIG_X is not set` 导致重复 key

**现象**：反复跑 sync 后，`.config` 里同一个 key 出现多行（一行 `=y`，一行 `# ... is not set`），
构建行为随机。

**根因**：Kconfig 关闭某项的写法是 `# CONFIG_X is not set`，脚本原来只匹配 `CONFIG_X=` 形式，
于是旧行留下的 `# ... is not set` 一直没被清掉。

**解决**：正则加上 `\s+is\s+not\s+set` 分支，并且**先删干净所有旧条目再写新条目**。
验收标准：`.config` 里每个 `LINK_SCOPE` 相关 key 只出现一次。

### P22 · 烧录时序

**现象**：BurnTool 点"烧录"后没反应，或者报失败。

**根因**：WS63 靠串口握手进下载模式，需要**在点开始后的几秒内给板上电或按复位**。

**流程**：BurnTool → 选 `ws63-liteos-app_all.fwpkg`（整包，`_load_only` 只是加载区）→
点烧录 → 几秒内上电/复位 → 等 `ret:0` → 再复位一次让它跑新固件。

**注意**：BurnTool 的 `log.txt` **不记录烧的是哪个 fwpkg**，只有波特率行和 `ret`。
所以要靠别的手段确认板上到底是什么固件（我们用 `.du` 文件里查符号，见 `firmware/scripts`）。

### P23 · 角色是编译期选的

**现象**：换角色（initiator / responder / loopback / timing）后直接烧录，板子行为没变。

**根因**：角色由 Kconfig 的 `CONFIG_LINK_SCOPE_ROLE_*` 决定，是**编译期**分支；
`.config` 改了但不重编，产物还是旧的。

**流程约束**：
1. 改代码 → `sync-to-sdk.ps1 -Role X` → **必须重编** → 烧
2. 两块板必须烧**不同角色**的固件（一 A 一 B），别烧串了
3. 每次编完把 fwpkg 归档到 `local_fw/linkscope/<角色>-<月日_时分>.fwpkg`，否则会被下次构建覆盖

### P19 · SDK 预编译库每包刷两行，会吃满串口

**现象**：A 板每发一个包，串口就多两行：

```
ssapc write rsp handle:2
[sle write_req_complete_cbk]conn_id:0, err_code:0
```

**根因**：这两行来自 **SLE 协议栈的预编译库**（在 SDK 源码里搜不到字符串），
没有编译开关、也没找到运行时 log level 接口能关掉。

**影响**（按实测比例算）：每包约 90 字节。当前 13Hz 时 ≈1.3KB/s，无所谓；
但真跑到 100Hz 就是 **200 行/秒 ≈ 9KB/s，占 115200 串口的约 78%**——
会把主循环拖慢、把时序搅乱，W1 的数据就不可信了。

**候选方案**（待验证）：
1. 把 console 波特率从 115200 提到 921600（`CONFIG_DEBUG_UART_BAUDRATE`，一行改动、一次编译），
   占用降到约 10%；采集端也要改波特率。
2. 降测量速率（50Hz），并在报告里写明速率就是 50Hz，不做"100Hz 名义值"的美化。
3. 若后续能找到库里的 log 宏/接口（如 `uapi_log_set_level`），直接关掉模块日志——最优。

### P20 · 连上了、写成功了，但一个 RSP 都收不到

**现象**（2026-11-06 09:00 双板实测）：

A 板一切正常：
```
[A] found linkscope rssi=217, stop seek
[A] connected conn_id=0x0 pair_state=1
[A] mtu=520
[A] property handle=0x2, link ready
```
之后 A 持续发写请求，**1421 次 / 108 秒 = 13.1Hz**，且 `write cfm error` 为 **0**（写请求本身成功）。
但 `# SUM` 一行都没有 → **收到 0 个有效 RSP**。

**已排除**：
- 不是没连上（有 connected / mtu / property handle）
- 不是没发出去（1421 次写、0 次写失败）
- 不是 A 重启（108 秒内 0 次 NMI）

**速率本身就是证据**：13.1Hz ≈ 1000ms ÷ (50ms 超时 + 开销) → 每个包都在等满超时。

> **注意（09:23 修正）**：上一条当时是当"铁证"用的，其实**不严密**。
> 看 `engine.c:19-45` 就能发现：`bad_frame`、`dup`（seq/t1 对不上）、`unsolicited` 三条拒绝路径
> **都不清 `pending`**，所以"RSP 到了但被拒"同样会走满 50ms 超时，同样是 13Hz。
> 只有 `recv` 会清 `pending`。所以 13Hz 只能证明"没有一帧被接受"，不能证明"一帧都没到"。
> 这是在拿到 B 侧心跳数据、回头重读代码时才发现的——**推论链条里最不该省的就是"代码里到底怎么走的"**。

**为什么 B 的日志是空的**：见 P24。

**已做的诊断**：在 `link_sle_responder.c` 里加 1 秒心跳，把 B 侧三个计数摊开
（`req` 写回调次数 / `bad` 解析失败次数 / `rsp` 成功调用 `ssaps_notify_indicate` 次数 / `lasterr` 错误码）。
心跳在**任务上下文**打印，不在回调里，不打乱 t2/t3。

**判读表**：

| B 的输出 | 结论 | 下一步 |
|---|---|---|
| `req=0` | 写回调没被调用 | 查服务/属性注册、写权限 |
| `req>0 bad=req` | 回调进了但解析失败 | 对比两侧帧格式/长度 |
| `req>0 rsp=req lasterr=0` | 通知发出去了，A 没收到 | 改 A 的接收侧 |
| `rsp=0 lasterr=0x…` | `ssaps_notify_indicate` 被拒 | 查 CCCD/通知使能 |

**2026-11-06 09:23 的实测结果（B 板心跳版，A 板未重编）**：

```
[B] hb req=1404 bad=0 rsp=1404 lasterr=0x0     09:22:57
[B] hb req=1562 bad=0 rsp=1562 lasterr=0x0     09:23:09   → 13.2 次/秒，与 A 的发包速率一致
```

三个结论：
1. **上行完全通了**：B 每秒收到的 REQ 数与 A 发出的数一致（13.2/s），说明写请求确实到达、回调被调用；
2. **B 的解析没问题**：`bad=0`，40B 的 REQ 全部被 `probe_parse_req` 接受；
3. **B 的回发调用全部返回成功**：`rsp=req`、`lasterr=0x0`，即 `ssaps_notify_indicate()` 每次都返回 0。

于是问题被夹到了 **B 的 notify 调用之后 → A 的 `notification_cb` 之前** 这一段，且
B 侧已经没有任何可查的返回值了（0 = 成功）。剩下的可能只有：
(a) 通知根本没上空中（协议栈把它吞了）；
(b) 上了空中但 A 的 `notification_cb` 没被调；
(c) 回调被调了，但帧被 engine 拒（见上面那条"13Hz 不严密"的修正）。

**2026-11-06 09:39 的实测结果（A 侧探针版）**：

```

09:39:14.387 [linkscope] no rsp yet: sent=584  recv=0 to=583  unsol=6  bad=0 dup=385
09:39:19.388 [linkscope] no rsp yet: sent=682  recv=0 to=681  unsol=7  bad=0 dup=449
…（每 5 秒一行，sent 与 dup 同步增长）
09:40:19.387 [linkscope] no rsp yet: sent=1865 recv=0 to=1864 unsol=10 bad=0 dup=1236
```

这一轮把 P20 的结论往前推了一大步，也**推翻了"一帧都没到"**：

1. **帧到了**：`first rsp` 打印了，`len=20`、`status=0x0`、前 4 字节 `a5 02 01 00`（magic/type/seq=1 全对）；
2. **不是格式问题**：`bad=0`，说明 `probe_parse_rsp` 每次都能接受；
3. **是被判成"迟到"**：`dup` 以约 19 次/秒 增长，与发包速率同步；
4. **只有 2/3 的包有回音**：`dup/sent ≈ 66%`，其余走满超时（`unsol` 只有 10，说明不是乱序）。

所以真相是：**RSP 每一帧都到，但都在 50ms 超时之后才到**——到达时 A 已经发下一包了，
`rsp.seq` 是上一包的，于是被 `seq != pending_seq` 判成 dup。

节拍也能对上：1865 包 / 65 秒 ≈ 19.7Hz ≈ 1 ÷ (50ms 超时 + 少量开销)。

**下一步（诊断版已 sync，等重编 A）**：不动逻辑，只加"被拒帧现场快照"——
`link_sle_responder.c` 的写回调本来就有 t2/t3，所以 `rej_bproc_us = t3-t2` 能告诉你 B 端的处理耗时（同一时钟，精确）；
`rej_age_us = t4 - rsp.t1` 就是这一帧的**真实 RTT**（A 同一时钟，精确）。
两者一比就能分清延迟到底在 B 的调度、还是在空口/协议栈。
同时把超时**临时**提到 500ms（`sync-to-sdk.ps1 -TimeoutMs 500`），让这些迟到的帧被接受、能直接打出 `# SUM` 和真实 RTT 分布。

**2026-11-06 10:28 的实测结果（超时 500ms，A 板诊断版；B 板心跳版不动）**：

```

# SUM n=400  p50=102734 p90=106306 p99=114264 p999=125053 max=125053 mean=101006 jit=2235 sent=401  recv=400  to=0 dup=0 bad=0 bproc=12/24 …

超时一放宽到 500ms，RSP 立刻全被接受（`to=0 dup=0`，20 秒 200 包 = 10Hz），
真相是 **RTT 整整 100ms**，比 50ms 超时大了一倍，所以之前每一帧都"迟到"。

两个结论：

1. **不是我们的代码**：`bproc = 12µs 平均 / 24µs 最大`——B 从写回调进来到发出 notify 只用 12µs，
   协议组包、解析、回填时间戳全都不是瓶颈；
2. **100ms 非常整齐**：p50=102.6ms，jit 只有 1.9ms，p99=113.7ms，max=125ms。
   整齐到不像"排队"，像**被链路调度间隔卡住**——默认连接间隔 `0x64` 单位 slot(125µs) 即 12.5ms，
   100ms ≈ 8 个间隔。

于是把 100ms 拆成两段来量（下一版固件）：

- `write cfm #n lat=… us`：`ssapc_write_req` 到 `write_cfm_cb` 的时延（A 本地时钟，精确）。
  这段小 → 上行快，慢在回程；这段大 → 上行本身就慢；
- 连上 30 秒后试一次 `sle_update_connect_param(interval=0x06 slot)`，并用 `connect_param_update_cb`
  打印内核真正给的间隔。**若 RTT 跟着掉下来，100ms 就是间隔卡出来的**，不是协议栈的固定开销。

**2026-11-06 10:42 的实测结果（改连接参数那一版）**：

从 B 板心跳反推的收包速率（B 的心跳每 0.5s 一行，`req` 是累计收到的写请求数）：

10:42:10  rate=23.8/s      ← 就是这一秒变的
10:42:19  rate=37.2/s      ← 改完：RTT≈27ms
10:42:29  rate=37.3/s
…
10:43:17  rate=22.7/s      ← 后面又掉到 18~22/s（RTT≈48ms）

A 板这一轮的 107 条样本（seq 3275–3381）：RTT 24ms×74、28ms×13、48ms×8、68ms×3，另有 8 个 272–300ms 的尖峰；
`bproc` 仍是 12µs。

三条结论：

1. **100ms 的元凶确实是连接间隔**：一改参数，速率从 10/s 跳到 37/s（RTT 100ms → 27ms），

3. **日志被厂商的预编译库冲掉了**（P19）：A 每发一个写请求，库里就打两行

所以下一版：每 20s 依次试 `0x06 / 0x18 / 0x30 / 0x40 / 0x64` 五个间隔，每次都打 `rc` 和

11:15:16.193 [A] tune slot=0x6 (750 us) rc=0x0
11:15:16.383 [A] param updated conn=0x0 intv=6 slot (750 us) latency=0 sup=3200
```

| A 请求的间隔 | 样本 | 速率 | p50 | p90 | 与间隔的倍数 |
| --- | --- | --- | --- | --- | --- |
| 0x40 = 8 ms | 101 | 14.4/s | **63.9 ms** | 71.8 ms | **8.0 ×** |
| 0x64 = 12.5 ms | 198 | 9.9/s | **99.9 ms** | 112.4 ms | **8.0 ×** |
| 0x06 = 0.75 ms | 115 | 6.1/s | **23.9 ms** | 100.3 ms | 32 ×（p90 更是 134 ×） |

结论（这一轮把 P20 从"是间隔"推进到"是 8 个事件，但还有第二个瓶颈"）：

1. **8 ms 和 12.5 ms 两档，RTT 精确等于 8 个连接事件**（63.94 / 8.0、99.94 / 12.5，误差 0.1%）。
   这不像 2 个事件，说明"请求发出去 → 写确认回来"这段被排了 8 个事件，
   写确认（`write cfm`）本身平均就有 28 ms，**慢在上行，不是回程**；
2. **间隔压到 0.75 ms 后 RTT 不再跟着掉**，卡在 ~24 ms；
   而且这一档 p90 直接跳到 100 ms、max 300 ms —— 0.75 ms 间隔下链路明显撑不住（重传/丢帧），
   速率反而掉到 6.1/s。**0.75 ms 不是一个可用档位**；
3. 两件事都要治：8 个事件的排队（上行慢）和 ~24 ms 的固定底。下一版把 `write cfm` 改成
   **每 5 秒一窗、报完清零**，就能单独看"每个间隔档下写确认是多少"，直接判定 24 ms 属于哪一段；
4. 顺手修了一个显示 bug：`tune` 行里的 `granted` 读的是上一次回调的值（滞后一拍），
   已改成 `prev_granted`，真值看 `param updated` 那行。

**2026-11-06 11:54 的实测结果（cfm 改 5 秒窗、日志完整落盘，375 秒 / 8274 条 S 行）**：

这一轮数据终于平稳了（每个窗口的 p50 几乎不动），把 5 个间隔档一次跑完：

| 间隔 | cfm 均值（写请求→写确认） | RTT p50 | RTT p90 | 速率 | RTT / 间隔 |
| --- | --- | --- | --- | --- | --- |
| 0.75 ms（0x06） | 18–19 ms | **23.97 ms** | 47.7 ms | 36–37/s | 32 ×（触底） |
| 3 ms（0x18） | 16.4 ms | **23.95 ms** | 24.1 ms | 40–41/s | 8.0 ×（= 底） |
| 6 ms（0x30） | 31.8 ms | **47.95 ms** | 53.9 ms | 20.4/s | 8.0 × |
| 8 ms（0x40） | 42.1 ms | **63.95 ms** | 71.9 ms | 15.2/s | 8.0 × |
| 12.5 ms（0x64） | 65–67 ms | **99.96 ms** | 112–125 ms | 9.6/s | 8.0 × |

三条结论：

1. **规律是 `RTT = 8 × 间隔`，下限 24 ms**（`max(8 × intv, 24ms)`）。
   6 / 8 / 12.5 ms 三档都是精确 8.0 倍；0.75 ms 和 3 ms 触到 24 ms 的底，**不再下降**——
   说明**实际生效的最小连接间隔是 3 ms**（0x06 报上去了、回调也回了 `intv=6`，但空口没有真的变快）；
2. **慢在上行**：`cfm`（A 发出写请求 → 收到写确认）稳定在 RTT 的 2/3 左右，
   也就是说一个来回里大部分时间花在"请求挤上去"，回程的 notify 只占小头；
3. **停止等模式的吞吐上限 ≈ 41 包/秒**（3 ms 档，40 字节载荷）。100Hz 需要的 10 ms 往返，
   现在的链路差了一倍多。**这不是调参能解决的**：8 个事件的排队是协议栈/空口的行为。

**这一条对方案的直接影响**（记在 P26）：要么改流水线（多个请求在途，按 seq 回收），
要么用 SDK 的 low latency TX（`sle_low_latency_tx_register_callbacks`，协议栈按率来拉数据），
要么把 100Hz 的目标下调到 40Hz。

### P26 · 停止等模式的往返底线 24 ms，吞吐上限 41 包/秒

**现象**：间隔一路往下压，RTT 却停在 24 ms 不再降；3 ms 档实测速率最高 40–41 包/秒。

**定位**：把 375 秒的完整日志按 5 秒窗口对齐 `cfm`（写请求→写确认）和 RTT，得到一条干净的规律：

```
RTT_p50 = max(8 × 连接间隔, 24 ms)
cfm     ≈ 2/3 × RTT
```

| 间隔 | cfm | RTT p50 | 速率 |
| --- | --- | --- | --- |
| 0.75 ms | 18–19 ms | 23.97 ms | 36–37/s |
| 3 ms | 16.4 ms | 23.95 ms | 40–41/s |
| 6 ms | 31.8 ms | 47.95 ms | 20.4/s |
| 8 ms | 42.1 ms | 63.95 ms | 15.2/s |
| 12.5 ms | 65–67 ms | 99.96 ms | 9.6/s |

**根因**：①**实际生效的最小连接间隔是 3 ms**——0x06（0.75 ms）报上去了、`param updated`
也回了 `intv=6 slot`，但空口没有更快，RTT 与 3 ms 档完全一样；②一个来回要排
**8 个连接事件**（6 / 8 / 12.5 ms 三档都是精确 8.0 倍，误差 <0.2%），且 `cfm` 占了 2/3，
说明时间花在"请求挤上去"，不是回程的 notify；③我们自己的引擎不是瓶颈：
tick 是 10 ms 一次，RTT 24 ms 时 pacing 根本不绑定（`to=0`、`sent=recv`）。

**影响**：100 Hz 需要 10 ms 往返，现在差一倍多。**这不是调参能解决的**，8 个事件的排队
在协议栈/空口里，停止等（一个在途、等回包）这个结构本身决定了上限 ≈ 1/RTT。

**候选出路**（都还没验证）：
(a) **流水线**：引擎允许多个请求在途、按 `seq` 回收，吞吐理论上按在途数放大；
(b) **low latency TX**：`sle_low_latency_tx_register_callbacks`（协议栈按率来拉数据，拉模式）；
(c) **下调目标**：把采样率定在 40 Hz 以内，接受 24 ms 的底。

**状态**：⏳ 未解决。

**2026-11-06 12:19 的验证：流水线没用（(a) 被证伪）**

给引擎加了在途窗口（`LINK_SCOPE_WINDOW`，1..8），用最激进的配置打：
`rate=1000Hz win=8 timeout=500ms`，A 只重烧固件、B 不动，跑 160 秒：

```
role=initiator (A)
link=sle cfg=0 payload=40B rate=1000Hz win=8 timeout=500ms
# SUM n=200  p50=168589 ... sent=638  recv=200  to=430 dup=430
# SUM n=4200 p50=166816 ... sent=4989 recv=4200 to=781 dup=781
```

- **吞吐没涨**：`sent` 每 4 秒 +200 ≈ **50 包/秒**（个别时段只有 20/s），
  和停等的 41 包/秒是同一个量级，**没有按窗口倍数放大**；
- **RTT 反而爆了**：p50 从 24 ms 涨到 **168 ms**，正好是 8 个包排队、按 50 包/秒 清空的结果
  （8 ÷ 50 ≈ 160 ms）；
- 还多出 `to=430 dup=430`：先发的包在栈里排队超过 500 ms 被判丢，它们的 RSP 后到又被记成 dup。

**结论**：这个链路的**可持续速率就是 ~41–50 个"请求-回包"对/秒**，
在途包数只会把队列堆长、把 RTT 抬起来，不会提高吞吐。8 个事件的排队是协议栈/空口
的行为，我们改不了。

**下一步（W2 起）**：只剩 (b) 一条真出路——SLE 的 low latency 数据通道
（`sle_low_latency_tx_register_callbacks`，按率拉数据）。但要提醒：**官方 SDK 里没有任何
一个样例真的用它**（`sle_uart.c` 只 `#include` 了头文件，client 里那句
`sle_low_latency_rx_enable` 只是一行打印），属于没有参考实现的区域，风险要高一个量级。
所以 W1/W2 的实测按 **40 Hz 档（3 ms 间隔）** 定，100 Hz 记为"已被 SDK 卡住"。

## 六、经验汇总（给后来的人）

1. **头文件里的宏不可信，实测才算数**（24 vs 40 ticks/µs；tick 10ms vs 20ms）。
2. **预编译库的打印关不掉**，所以串口带宽要在设计阶段就算，别等跑满了才发现。
3. **忙等 + 看门狗 = 必须自己喂**，而且喂狗点要放在"正事干完"之后。
4. **先确认串口路径**（console UART0 / log UART1），再下"板子没动"的结论。
5. **协议两端要能独立自测**：主机单测 + 同步 loopback 链路，把协议/引擎的 bug 在双板联调之前清掉。
   本项目主机单测 47 项（selftest 32 + 集成 15），抓到 P13、P14 两个真 bug。
6. **每换角色就重编**，归档产物，否则现场分不清板上是什么。
7. **一个数据点要能自证**：`seq` 连续就说明没重启，`sent=recv` 就说明没丢包——
   设计输出格式时就把这些"自证字段"带上，比事后猜强得多。
8. **采集前先验证落盘**：串口工具的窗口只留最后几秒，存日志开关默认关着（P25），
   不然跑得越久、丢得越多，而且丢掉的那段永远补不回来。

### P27 · 固定间隔档要等链路就绪 20 s 才生效，前 25 s 积压 600 包全部超时

**现象**：W1 正式基线那一轮（`cfg=0 / 40B / 40Hz / 3ms`），日志开头的 25 秒里
`recv=0`、`to` 与 `dup` 一路涨到 592，`no rsp yet` 连报 6 次；之后突然全部正常，
40 次/秒、0 超时跑满 11 分钟。同一轮数据前半段是垃圾、后半段是金子。

**现场**：
```
19:17:03  no rsp yet: sent=90   recv=0 to=89  dup=56
19:17:08  no rsp yet: sent=190  recv=0 to=189 dup=120
19:17:13  no rsp yet: sent=289  recv=0 to=288 dup=182
19:17:18  no rsp yet: sent=389  recv=0 to=388 dup=246
19:17:23  [A] tune slot=0x18 (3000 us) rc=0x0 (prev_granted=0xffff)   ← 到这一刻才谈参数
19:17:28  no rsp yet: sent=587  recv=0 to=586 dup=578
19:17:34  # SUM n=200 ... to=591 dup=591                             ← 之后清零，恢复正常
```
被拒帧的现场快照 `rej: rsp_seq=56 pend_seq=90 age_us=1729204 bproc_us=12`：
`age` 从 1.7 s 一路涨到 7.2 s（每包多积压约 18 ms），而 `bproc` 始终 8–15 µs。

**定位**：`age` 是"从发出到收回"的真实时长（同机、同一时钟），1.7–7.2 s 说明
请求在**上行**就排队了，不是回程慢；`bproc` 只有十几微秒，B 端一点问题没有。
再看时间线：`tune slot=0x18` 出现在 19:17:23，而 `link ready` 是 19:16:59 —— 正好差 24 秒。

**根因**：`sle_poll()` 里有个 20 s 节流（`LS_INTV_SWEEP_US`），
而 `on_find_property()` 把 `g_last_tune_us` 设成了 `g_ready_us`，于是**固定档位也要等 20 s 才生效**。
这 20 s 链路跑在默认的 12.5 ms 间隔上（`RTT = 8 × 12.5 = 100 ms`），
而探针按 40 Hz（25 ms 一个）在发、超时 50 ms 就判死再发下一个 —— 发送速率是链路能力的 4 倍，
停止等模式又没有背压，于是队列越积越长，等到第 24 秒参数终于改成 3 ms，积压的 600 个请求
在两秒内被排空，全部以"迟到 1.7–7 s"的形态被判 `dup`。

**解决**（三处，改完语法检查 9/9）：
1. `link_sle_initiator.c` `on_find_property()`：固定档位时把 `g_last_tune_us` 回拨一个扫描周期
   （`g_ready_us - LS_INTV_SWEEP_US`），**就绪立刻谈参数**，不等 20 s；
2. `linkscope_main.c`：`poll` 节拍从 5 s 降到 1 s（新宏 `LS_POLL_MS`），
   写确认统计仍按 5 s（`LS_DBG_MS`），两个定时器分开；
3. `sle_poll()`：若 `g_granted_intv` 已经是目标档，直接返回 —— 谈成了就别再周期性打扰链路。

**验证**：待重编重烧后的下一轮（预期预热从 25 s 缩到 1 s 内，`to/dup` 应为个位数）。

**教训**：固定配置的"生效时刻"本身也是配置的一部分。做基线前先看日志开头有没有
`param updated intv=...`，没有就别开始计时。


**2026-11-06 19:52 验证：修复生效**

同一配置重编重烧 A 后复测 309 秒：

```
19:52:58.993  [A] property handle=0x2, link ready
19:52:59.575  [A] tune slot=0x18 (3000 us) rc=0x0      ← ready 后 0.6s 就谈参数（原来 24s）
19:52:59.716  [A] param updated conn=0x0 intv=24 slot (3000 us)
首条 SUM: to=17 dup=17                                  ← 只有参数生效前那 0.7 秒的代价（原来 592）
末条 SUM: to=17 dup=17 sent=12217 recv=12200            ← 稳态 0 丢包
稳态 n=12170 p50=23908 p90=24656 p99=27048 stdev=1016
```

结论：预热从 25 s 压到 0.7 s，代价从 592 包压到 17 包；稳态分位数与修复前逐位相同
（p50 23.908 vs 23.914 ms），证明修复只消掉了"参数生效前的空窗"，没有改变链路行为。
签收：✅ 已解决，W1 基线以 19:52 这轮为准（见 W1-平台能力确认.md §5.4）。

### P38 · Write Request 确认诊断每5秒重复打印，污染严格 A/B

**发现时间**：2026-11-09，验收第一轮 Write Request 双板日志。

**现象**：源码注释要求只打印启动后的前3次写确认，但日志中出现318条 `write cfm #1/#2/#3`。
`on_write_cfm()` 用 `g_cfm_n <= 3` 控制打印，而 `sle_dbg()` 每5秒为窗口统计把 `g_cfm_n` 清零，
于是每个统计窗口都会再次打印3条。

**影响**：Request 轮比 Command 轮多出周期性 UART 输出。虽然频率只有约0.6行/秒，不能据此解释约9 ms
的 RTT 差异，但它破坏了“只改变写语义”的严格实验条件，因此 run1 只作为预实验，不签收最终 A/B。

**run1 观测**：21,000个有效响应，RTT p50/p90/p99 为23.638/25.579/28.109 ms；稳态无新增超时、
坏帧或断链；写确认窗口均值大多约16 ms。原始证据保存在 `artifacts/logs/M1/write_req_run1/`。

**解决**：新增独立的 `g_cfm_print_n`，它只控制启动后前三条诊断且不随5秒统计窗口清零；
`g_cfm_n/sum/max` 继续按窗口清零，不改变确认统计口径。

**验证**：主机 selftest `pass=32 fail=0`、engine tests PASS；Request 配置下使用当前 SDK 真头文件的
13个 C 文件全部通过。尚需 Ubuntu 完整构建并复测 Request。

**完整构建（2026-11-09）**：修复版 RISC-V 固件完成链接、签名和打包，日志以
`Build target:ws63_liteos_app success`、`packet success!` 结束。Z: 源包连续两次哈希一致，包内身份为
`role=initiator / sle-write_req`，且哈希与 run1 不同：
